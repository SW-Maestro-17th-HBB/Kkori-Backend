# 면접관 에이전트 디스패치

> **User Story**: HBB1-289 — 나는 사용자로서 면접 세션을 생성할 수 있다.
>
> **하위 이슈**: HBB1-290 [개발] 세션 컨텍스트 metadata 조립 개발 · HBB1-291 [개발] 명시 디스패치 전환 개발

## Overview

본 기능은 세션 생성(`POST /api/v1/sessions`) 완료 시점에 **면접관 AI 에이전트(Kkori-AI)를 세션 룸에 명시적으로 디스패치**하는 흐름을 정의한다. `interview-session-creation.md`(HBB1-18)가 확립한 생성 파이프라인의 **커밋 후 단계를 확장**하는 스토리다 — 어긋나는 부분은 본 문서가 우선한다(요청·응답 계약, 트랜잭션 경계, 룸·토큰 규칙 등 개정하지 않은 부분은 그대로 계승).

현재 AI 워커는 `agent_name` 미등록 상태의 **자동 디스패치**로 모든 룸에 입장하는 임시 구조다 — 어떤 세션의 룸인지, 어떤 면접 유형인지 워커가 알 수 없다. 본 스토리로:

- AI 워커는 `agent_name`을 등록해 자동 디스패치를 끄고, **Spring이 명시 디스패치(`createDispatch`)의 주체**가 된다.
- 디스패치 metadata로 **세션 컨텍스트**(세션 식별자·면접 유형·직무·이력서 컨텍스트)를 전달한다 — AI 파이프라인 분기(유형·직무)와 이력서 기반 질문 개인화의 입력이며, 워커의 metadata 파싱(`parse_job_metadata`)은 이미 구현되어 있다.
- 프론트 계약은 변경하지 않는다 — 요청·응답 모두 HBB1-18 그대로.

### 기능 요구사항

| No. | Function | Description |
| --- | --- | --- |
| 1 | 세션 컨텍스트 metadata 조립 | 세션 속성과 이력서 `structured_data`에서 디스패치 metadata(JSON)를 코드로 조립해야 한다(LLM 미사용). 이력서 없음·`structured_data` 부재·부분 결손을 모두 허용한다. |
| 2 | 명시 디스패치 전환 | 커밋 후 토큰 발급 성공 다음에 `createDispatch(room, agentName, metadata)`를 호출해야 한다. 실패는 신설 `S004`로 응답하며 토큰 실패(`S001`)와 동일한 보상 모델을 따른다. |

### 디스패치 계약 (Kkori-AI 공유 — 임의 변경 금지)

Kkori-AI 레포와 공유하는 크로스 레포 계약이다. 변경은 양 레포 합의·동시 반영으로만 한다.

- **agent_name**: `kkori-interviewer` — 코드 상수로 고정한다(설정 프로퍼티 아님). 환경별로 달라질 값이 아니라 계약값이며, 설정화하면 오배포로 계약이 깨지는 경로만 늘어난다.
- **metadata**: JSON 객체, 필드는 아래 4개가 전부다.

| 필드 | 타입 | 필수 | 값 |
| --- | --- | --- | --- |
| `sessionId` | string | 필수 | 세션 id(Long)의 문자열화 (예: `"123"`) |
| `interviewType` | string | 필수 | enum 이름 그대로 (`THIRTY_MIN`/`FIVE_MIN`) |
| `position` | string | 필수 | enum 이름 그대로 (`BACKEND`/`FRONTEND`) |
| `resumeContext` | string | 조건부 | `structured_data`에서 조립한 이력서 컨텍스트 텍스트. **없으면 필드 자체를 생략**한다(null·빈 문자열 금지) |

- `resumeContext` 포함 여부는 **면접 유형이 아니라 이력서 데이터 존재 기준**이다: 세션에 `resume_id`가 없거나(이력서 미제출 `FIVE_MIN`) 해당 이력서의 `structured_data`가 없으면 생략하고, 있으면 유형 무관 포함한다(`resumeId`를 제출한 `FIVE_MIN` 포함).
- **`resumeContext` 원문은 개인정보다** — 운영 로그 어디에도 남기지 않는다(기능 1 기타 요구사항).

#### 계약 픽스처 (canonical sample)

아래 샘플은 **양 레포 테스트가 공유하는 계약 픽스처**다 — 백엔드는 조립 결과가 이 문자열과 **자구까지 일치**함을, AI 레포는 이 문자열의 파싱을 검증한다. 문구 하나라도 바꾸면 계약 변경이다.

샘플 값 자체는 합성이지만 Worker 실산출물의 특성을 반영한다(구조화 프롬프트 규칙 — Kkori-AI `providers.py`): 스키마는 양 레포 계약 정의(`StructuredData.java` ↔ `contract/structured_data.py`)와 일치하고, 결손 항목은 null·필드 누락이 아닌 **빈 값**(빈 문자열·빈 배열)으로 나타나며, `description`은 **원문 표현 보존**(요약 없음)이라 길고 개행을 포함할 수 있고, 기술명은 원문 표기 그대로다.

입력 `structured_data`:

```json
{
  "profile": { "name": "홍길동", "email": "hong@example.com" },
  "skills": [
    { "category": "언어", "items": ["Java", "Python"] },
    { "category": "프레임워크", "items": ["Spring Boot"] }
  ],
  "projects": [
    { "name": "Kkori", "role": "백엔드", "description": "AI 면접 준비 서비스의 세션 생성 API와 LiveKit 실시간 음성 연동을 설계·구현. user 행 잠금 기반 동시성 제어로 유저당 단일 세션 불변식을 보장", "techStacks": ["Spring Boot", "PostgreSQL"] }
  ],
  "experiences": [
    { "title": "ABC 커머스 인턴", "description": "결제 정산 배치의 지연 문제를 인덱스 재설계로 개선하고 처리 시간을 40% 단축" }
  ]
}
```

세션 id 123, `THIRTY_MIN`, `BACKEND`일 때의 디스패치 metadata(직렬화 자구 — compact, 필드 순서 고정):

```json
{"sessionId":"123","interviewType":"THIRTY_MIN","position":"BACKEND","resumeContext":"[기술 스택]\n- 언어: Java, Python\n- 프레임워크: Spring Boot\n\n[프로젝트]\n- Kkori (백엔드): AI 면접 준비 서비스의 세션 생성 API와 LiveKit 실시간 음성 연동을 설계·구현. user 행 잠금 기반 동시성 제어로 유저당 단일 세션 불변식을 보장 (기술: Spring Boot, PostgreSQL)\n\n[경험]\n- ABC 커머스 인턴: 결제 정산 배치의 지연 문제를 인덱스 재설계로 개선하고 처리 시간을 40% 단축"}
```

`resumeContext` 텍스트를 풀어 쓰면 (참고용 — 계약 자구는 위 JSON):

```
[기술 스택]
- 언어: Java, Python
- 프레임워크: Spring Boot

[프로젝트]
- Kkori (백엔드): AI 면접 준비 서비스의 세션 생성 API와 LiveKit 실시간 음성 연동을 설계·구현. user 행 잠금 기반 동시성 제어로 유저당 단일 세션 불변식을 보장 (기술: Spring Boot, PostgreSQL)

[경험]
- ABC 커머스 인턴: 결제 정산 배치의 지연 문제를 인덱스 재설계로 개선하고 처리 시간을 40% 단축
```

이력서 없는 세션(id 124, `FIVE_MIN`, `FRONTEND`)의 metadata:

```json
{"sessionId":"124","interviewType":"FIVE_MIN","position":"FRONTEND"}
```

## 세션 컨텍스트 metadata 조립

### 설명

세션 속성(세션 id·면접 유형·직무)과 대상 이력서의 `structured_data`(`resumes.structured_data` jsonb — 스키마는 `resume.domain.StructuredData`가 유일 정의)에서 디스패치 metadata JSON을 조립해야 한다. **순수 코드 조립이며 LLM·외부 호출을 하지 않는다.**

**`resumeContext` 조립 규칙**:

- **입력은 `skills`·`projects`·`experiences`만이다** — `profile`(이름·이메일)은 **제외**한다. 질문 개인화에 불필요한 직접 식별자를 에이전트로 보내지 않는다(개인정보 최소화).
- 섹션 구성(순서 고정): `[기술 스택]`(skills) → `[프로젝트]`(projects) → `[경험]`(experiences). 각 섹션은 헤더 줄 + 항목 불릿(`- `) 줄들로 구성하고, 섹션 사이는 빈 줄 1개로 구분한다. 전체 텍스트에 선행·후행 개행을 두지 않는다.
- **정규화 — 모든 문자열 값에 조립 전 공통 적용**: ① 개행(CRLF·CR·LF)·탭을 공백으로 치환 ② 연속 공백을 공백 1개로 통합 ③ 앞뒤 공백 제거 ④ 결과가 빈 문자열이면 그 값은 **결손**(공백만 있는 값 포함). 배열은 요소별 정규화 후 결손 요소를 제거하고, 남는 요소가 없으면 배열 자체가 결손이다. Worker의 `description`은 원문 표현 보존이라 개행·연속 공백을 포함할 수 있는데, 그대로 두면 불릿·섹션 구조(줄 단위 파싱 가능성)가 깨진다.
- **항목 조립 — 유효 조각의 조건부 결합**: 항목마다 아래 세 조각을 정규화된 값으로 만들고(결손 필드가 낀 조각은 그 부분을 뺀다), 남은 조각을 규칙대로 결합한다. "자연스럽게 생략" 같은 구현 재량 없이 이 규칙이 산출 자구를 결정한다.

  | 항목 | 선두부 | 본문 | 꼬리 |
  | --- | --- | --- | --- |
  | skill | `{category}` | `{items를 ", "로 연결}` | — |
  | project | `{name} ({role})` — `role`은 `name`이 있을 때만 붙이고, `name` 결손 시 `role`은 버린다 | `{description}` | ` (기술: {techStacks를 ", "로 연결})` |
  | experience | `{title}` | `{description}` | — |

  - 선두부·본문이 모두 있으면 `{선두부}: {본문}`, 한쪽만 있으면 콜론 없이 그것만 쓴다.
  - 꼬리는 선두부·본문 중 하나 이상 있을 때만 뒤에 붙인다 — **꼬리만 남는 항목**(예: `techStacks`만 있는 project)은 항목째 생략한다.
  - 선두부·본문이 모두 결손이면 항목(불릿 줄)을 생략하고, 섹션의 항목이 전무하면(누락·빈 배열 포함) 섹션 전체(헤더 포함)를 생략하며, 세 섹션이 전부 생략되면 `resumeContext` 필드 자체를 생략한다(`structured_data` 부재와 동일 취급).
- **부분 결손 허용** — `structured_data`는 LLM 구조화 결과라 어떤 필드든 비어 있을 수 있다(형태는 엄격, 내용은 관대 — resume PRD §4 계승). **결손의 실제 형태는 두 갈래다**: Worker는 없는 항목을 null이 아닌 **빈 값**(빈 문자열·빈 배열)으로 기록하고(구조화 프롬프트 규칙), 사용자 수정(PATCH parsed)은 **필드 누락(null)**을 만들 수 있다 — 정규화·조립은 null·빈 문자열·빈 배열·공백만 값을 모두 동일하게 "결손"으로 취급한다.
- 조립에 사용하는 `structured_data`는 **세션 생성 트랜잭션이 이력서를 검증하며 읽은 값**이다 — 검증(EMBEDDED 확인)과 같은 user 잠금·트랜잭션 스냅샷에서 읽어 조립 입력의 일관성을 보장하고, 커밋 후 단계(디스패치)로 전달한다. 커밋 후 재조회하지 않는다. 구현 주의: 조립 입력 확보는 `PENDING` 교체 벌크 UPDATE **이전에** 마친다 — 벌크 UPDATE가 영속성 컨텍스트를 비워 앞서 조회한 엔티티가 detach된다(기존 `SessionService` 주석의 함정. 이미 로드된 기본 필드의 읽기 자체는 detach 후에도 동작하지만, 순서를 고정해 함정 근처를 지나지 않는다).

**JSON 직렬화**:

- 직렬화 자구는 세 가지로 고정한다: **compact**(공백 없음) · **필드 순서 고정**(`sessionId` → `interviewType` → `position` → `resumeContext`) · **비ASCII 원문 유지**(한글을 `\uXXXX`로 이스케이프하지 않음). 파싱 의미상 셋 다 무관하지만, 계약 픽스처의 자구 일치 검증(양 레포 테스트 공유)을 위해 산출 자구를 고정한다.
- Jackson 기본 직렬화는 세 규칙을 모두 충족한다. 반면 Python 기본(`json.dumps`의 `ensure_ascii=True`)은 비ASCII를 이스케이프하므로, AI 레포에서 픽스처를 재생성할 때는 `ensure_ascii=False`를 명시해야 자구가 일치한다. 그 외 이스케이프 세부는 표준 JSON 직렬화를 따른다.

### 검증 기준

- 계약 픽스처의 `structured_data` + 세션 속성(123·`THIRTY_MIN`·`BACKEND`) 입력 시 조립 결과가 픽스처 metadata JSON과 **자구까지 일치**하는지 확인 (계약 픽스처 테스트)
- 이력서 없는 세션(`FIVE_MIN`·`resumeId` 미제출) 입력 시 결과가 `resumeContext` 없는 픽스처 JSON과 자구까지 일치하는지 확인
- `structured_data`가 NULL인 이력서 → `resumeContext` 필드 생략 확인
- `resumeId`를 제출한 `FIVE_MIN` 세션 → `resumeContext`가 포함되는지 확인 (포함 기준은 유형이 아니라 이력서 데이터)
- 부분 결손 케이스: 일부 섹션만 존재(예: skills만) → 존재 섹션만 포함, 항목 필드 일부 결손 — null과 빈 값 양쪽 모두(예: project의 `role` null·`techStacks` 빈 배열) → 해당 조각만 생략, 빈 배열 섹션 → 섹션 생략, 전 섹션 결손(빈 값뿐) → `resumeContext` 생략 확인
- 선두 필드 결손 케이스(예: `name` 없는 project, `category` 없는 skill) → 콜론 없이 나머지로 불릿이 구성되는지 확인
- 정규화 케이스: `\r\n`·탭·연속 공백 포함 `description`이 공백 1개로 접혀 항목이 한 줄로 유지되는지, 공백만 있는 값·`items` 내 빈 문자열이 결손으로 제거되는지, `techStacks`만 있는 project(꼬리만 남음)가 항목째 생략되는지 확인
- 어떤 입력에서도 `profile`의 이름·이메일이 metadata에 포함되지 않는지 확인

- 산출물: 디스패치 계약의 metadata JSON 문자열 (Overview 계약 참조)

### 제약사항

- `resumeContext`의 절단(truncation)·사전 크기 검사는 두지 않는다 — LiveKit agent 디스패치 metadata 한도는 **512KiB**(공식 문서: "The metadata field is a string, limited to 512 KiB")이고, 실제 입력은 두 경로 모두 이에 한참 못 미친다: 사용자 수정(PATCH parsed)은 직렬화 100KB 상한이 서버에서 강제되고(resume PRD — `ResumeParsedService`), Worker 산출물은 구조화 LLM 호출의 `max_tokens`(4096)에 사실상 수 KB로 묶인다. 다만 후자는 계약이 아닌 구현 사정이므로 "초과 불가"를 계약 수준으로 단정하지는 않는다 — 만에 하나 초과하면 Cloud가 디스패치를 거부해 `S004`로 시끄럽게 표면화되며(조용한 절단으로 잘린 이력서 면접을 진행하는 것보다 낫다), 실측되면 그때 상한의 계약화(Worker 측 강제)를 검토한다.

### 기타 요구사항

- **`resumeContext` 원문(및 그것이 포함된 metadata 전문)은 운영 로그에 남기지 않는다** — 이력서 내용은 개인정보다. 디스패치 관련 로그는 세션 id·룸 이름 등 식별자만 기록한다.
- 조립은 세션 도메인 컴포넌트가 담당한다 — LiveKit SDK를 알지 않으며(벤더 무관 순수 조립), 디스패치 어댑터(기능 2)와 분리한다.

## 명시 디스패치 전환

### 설명

세션 생성 파이프라인의 **커밋 후, 토큰 발급 성공 다음**에 에이전트 디스패치를 호출해야 한다. HBB1-18의 처리 순서를 다음과 같이 확장한다(밑줄이 본 스토리 추가분):

> [트랜잭션 전] 룸 선생성 → [트랜잭션] 검증·`PENDING` 교체·INSERT(+ <u>metadata 조립 입력 확보</u>) → 커밋 → [커밋 후] 토큰 발급 → <u>**에이전트 디스패치**</u> → 교체된 기존 룸 정리(best-effort) → 응답

- **호출**: `createDispatch(룸 이름, "kkori-interviewer", metadata, JRP_NEVER)` — LiveKit Server API(`AgentDispatchServiceClient`, 현행 livekit-server 0.14.0) 왕복.
- **재시작 정책은 `JRP_NEVER`를 명시**한다 — restartPolicy를 생략하는 3인자 오버로드는 protobuf 기본값 `JRP_ON_FAILURE`(=0)로 전송되어, 에이전트 job 실패 시 LiveKit이 자동 재실행할 수 있다. 에이전트 이탈 복구는 범위 밖(후속 상태 머신 스토리의 `AGENT_LOST` 재디스패치 소관)이므로, 상태 머신·webhook 해석에 모델링되지 않은 자동 복구 경로를 명시적으로 차단한다. 재시작 정책 활용 여부는 복구 스토리에서 재검토한다.
- **순서 근거**: 토큰 발급(로컬 서명·사실상 설정 오류 수준으로만 실패)을 먼저 확정해, 유저가 입장할 수 없는 룸에 에이전트만 입장시키는 상태를 만들지 않는다. 디스패치가 마지막 가변 단계이므로 디스패치 성공 후 실패하는 후속 단계가 없다(기존 룸 정리는 best-effort — 응답에 무영향).
- **실패 모델 (`S004`, 토큰 실패 `S001`과 동일)**: 신규 룸을 보상 삭제한 뒤 `500 SESSION_DISPATCH_FAILED`로 응답한다. 커밋된 신규 `PENDING`과 확정된 교체는 유지되며, 잔존 `PENDING`은 다음 생성의 자동 교체가 수렴시킨다(HBB1-18 실패 모델 계승). **모호한 디스패치(타임아웃이지만 실제 성립)의 잔여물은 룸 보상 삭제 + `JRP_NEVER`가 실질 무해화하지만, 완전 소멸을 단정하지는 않는다** — dispatch는 룸과 별개 자원(전용 Delete/List API 존재)이라 룸 삭제가 계류 dispatch의 취소까지 보장한다는 공식 문서 근거가 없다. 잔여 위험의 상한: `S004` 응답은 500이라 토큰이 클라이언트에 전달되지 않았으므로 그 룸에 유저가 입장할 경로가 없고, `JRP_NEVER`라 실패 job의 재실행도 없다 — 최악은 뒤늦게 소비된 dispatch가 에이전트만 있는 룸을 잠시 만들었다 자연 소멸하는 것(유저 영향 없음, 워커 자원 낭비뿐). `deleteDispatch` 보상은 정작 모호한 케이스에서 응답(dispatchId)이 유실되어 성립하지 않고, `listDispatch` 조회 보상은 보상 자체의 실패 모드를 늘려 MVP에서는 두지 않는다 — 수동 검증에서 잔존·재실행이 실측되면 그때 `listDispatch` 보상 도입을 검토한다. 운영 탐지는 룸 단위 조회(`lk dispatch list <룸 이름>`)로 하며, 점검할 룸 이름은 `S004` 로그·`interview_session.livekit_room`에서 확보한다(삭제된 룸은 `lk room list`에 나타나지 않는다).
- **승계(superseded) 재확인**: 디스패치 성공 후 응답 전에 세션이 여전히 `PENDING`인지 재확인하고, 교체(`ABORTED`)가 감지되면 자신의 룸을 보상 삭제한 뒤 `409 SESSION_SUPERSEDED`(S005)로 끝낸다. user 잠금은 트랜잭션 구간만 직렬화하므로 커밋~디스패치 사이에 동일 유저의 후속 생성이 이 세션을 교체하고 룸까지 삭제할 수 있는데, **`createDispatch`는 미존재 룸을 자동 생성하므로**(2026-07-30 실측 확인) 늦은 디스패치가 삭제된 룸을 에이전트 있는 좀비 룸으로 되살리고, 교체된 세션의 요청까지 성공 응답을 받게 된다. 재확인 실패 시의 룸 보상 삭제가 그 재생성 룸과 agent job을 함께 소멸시키고(`JRP_NEVER`라 재실행 없음 — 실측 확인), "재시도·중복 요청에서는 마지막 생성 세션이 유효" 정책(HBB1-18)이 응답 계약으로도 성립한다. 교체가 재확인 이후에 오는 경우는 정상 교체 흐름과 같다 — 이 시점엔 룸·디스패치가 실존하므로 교체측의 룸 삭제가 항상 실효적이다(선생성 불변식의 확장).
- **응답 검증**: 어댑터는 2xx라도 응답의 생성된 `AgentDispatch`(id 비어 있지 않음·room·agent_name이 요청과 일치)를 확인하고, 빈(default)·불일치 응답은 `S004`로 다룬다 — 성공 계약은 "생성된 AgentDispatch 반환"이며, 빈 바디를 성공으로 삼으면 job 생성 여부를 모른 채 성공 응답을 반환하게 된다.
- **타임아웃·재시도**: 룸 생성·삭제와 동일 — `livekit.api-timeout`을 걸고 재시도하지 않는다. 호출은 트랜잭션·잠금 밖이므로 타임아웃은 요청 응답 지연의 상한이다.
- **어댑터 격리**: 도메인 서비스는 "에이전트 디스패치" 추상 인터페이스(세션 도메인)에만 의존하고, LiveKit SDK 호출은 벤더 어댑터(`global.livekit`)에 격리한다 — `SessionRoomManager`/`SessionTicketIssuer`와 동일 구조. 어댑터는 `LiveKitRoomManager`의 방침을 그대로 따른다: 로깅 인터셉터 없는 OkHttp 직접 공급(API Secret 파생 헤더 로그 방지), 실패 예외의 원인 미포장(유출 방지), 실패 로그는 룸 이름·HTTP 코드 등 식별자만(metadata 전문 금지 — 기능 1 기타 요구사항).
- **세션 상태는 변경하지 않는다**: 디스패치 성공 후에도 세션은 `PENDING`에 머문다 — `ACTIVE` 전이는 webhook 스토리(범위 밖) 소관이며, **본 스토리에서 세션이 `PENDING`인 것은 정상이다**. `PENDING`의 의미는 "룸·토큰 준비 완료, Agent 접속 전"(HBB1-18)에서 "…+ 디스패치 요청 완료, Agent 접속 확인 전"으로 자연 확장되지만 상태값·전이는 그대로다.

**Kkori-AI 연계 (전환 조정)**:

- 명시 디스패치가 워커에 도달하려면 AI 워커가 `agent_name="kkori-interviewer"`로 등록되어 있어야 한다. 등록은 워커의 자동 디스패치를 끄므로 **양 레포의 전환은 함께 이뤄져야 한다** — 어긋난 조합의 과도기 동작은 다음과 같고, 어느 쪽도 데이터 손상은 없다:
  - AI 미등록 + Spring 디스패치: 명시 디스패치는 수신 워커가 없어 **계류(`JS_PENDING`)로 남을 수 있고**, 면접은 기존 자동 디스패치가 metadata 없는 job으로 진행한다(워커의 `parse_job_metadata`는 metadata 부재를 이미 허용 — 현행과 동일한 무컨텍스트 면접). 단, **계류분은 워커가 등록되는 순간 뒤늦게 할당될 수 있다** — 전환 창에 생성된 세션의 룸이 아직 살아 있으면 진행 중 면접에 에이전트가 추가 입장(이중 에이전트)하는 경로가 열린다. 계류 dispatch의 유지 기간·후속 할당 여부는 공식 문서가 확정하지 않으므로 전환 절차로 방어한다.
  - AI 등록 + Spring 미디스패치(구버전): 에이전트가 입장하지 않아 면접이 시작되지 않는다 — **이 조합만 피한다**: AI 워커의 `agent_name` 등록은 본 기능이 포함된 백엔드가 배포된 뒤에 반영한다.
- **전환 절차(dev)**: ① 무사용 시간대에 백엔드 먼저 배포 ② **워커 등록 전에** 계류 dispatch를 정리한다 — 전환 창에 생성된 세션의 룸 이름을 DB에서 뽑아(`interview_session.livekit_room` — 전환 창 `created_at` 기준) 룸별로 `lk dispatch list <룸 이름>`으로 확인하고, 발견 시 `lk dispatch delete <룸 이름> <dispatch id>`로 삭제 ③ AI 워커 `agent_name` 등록 배포 ④ 새 세션 1건으로 정상 디스패치(단일 에이전트 입장) 확인. **정리가 등록보다 앞서는 이유**: 계류분은 워커가 등록되는 순간 할당될 수 있으므로 등록 후 정리는 이미 늦다. ②와 ③ 사이에 생성된 세션의 계류분이 이론상 남을 수 있으나 무사용 시간대라 실질 0이고, 의심되면 등록 직후 **점검(상태 확인)만 반복한다 — 삭제 규칙은 등록 전후가 다르다**: 등록 전에는 발견되는 계류분(`JS_PENDING`)을 그대로 삭제해도 안전하지만(할당 주체인 워커가 아직 없다), 등록 후에는 잔여 계류분이 이미 할당(`JS_RUNNING`)됐을 수 있어 **무조건 삭제하면 정상 면접의 에이전트를 종료할 수 있으므로 자동 삭제하지 않는다** — `JS_RUNNING` 발견 시 룸 생성 시각(워커 등록 시각 **이전**에 생성된 룸만 전환 잔여물 후보다)·참가자·자동 디스패치 에이전트와의 공존 여부를 확인한 뒤 수동 판단으로 처리한다. `lk dispatch list`는 룸 단위 명령이라 전역 조회가 없고 삭제된 룸은 `lk room list`에 나타나지 않으므로, 점검 대상 룸 이름의 출처는 DB다. dev 단계는 내부 사용자뿐이라 전환 창 트래픽이 사실상 0이므로, 디스패치 기능 게이트·전환 중 생성 차단 같은 장치는 설정 표면만 늘려 두지 않는다. 로컬은 양 레포를 함께 띄우므로 해당 없음.

### 실행 조건

- LiveKit Cloud 설정(`livekit.*` — HBB1-18/HBB1-256 계약 계승)이 충족되어야 한다. **신규 설정·환경변수는 없다** — 디스패치는 룸 생성과 동일한 자격증명·타임아웃(`livekit.api-timeout`)을 사용한다(배포 환경변수 매니페스트 변경 없음).
- 에이전트가 실제로 입장하려면 `kkori-interviewer`로 등록된 Kkori-AI 워커가 해당 LiveKit 프로젝트에 연결되어 있어야 한다 — 단, 워커 부재는 디스패치 API 오류가 아니므로(계류) 세션 생성은 성공한다.

### 검증 기준

- 정상 생성 시 디스패치 어댑터가 **토큰 발급 성공 후** 세션의 룸 이름·`kkori-interviewer`·조립된 metadata로 1회 호출되는지 확인
- 디스패치 요청의 재시작 정책이 `JRP_NEVER`로 명시되는지 확인 (어댑터 테스트 — 요청 수준 검증)
- 2xx라도 빈(default)·불일치 `AgentDispatch` 응답이면 `S004`로 매핑되는지 확인 (어댑터 응답 검증)
- 커밋과 응답 사이에 동시 생성이 세션을 교체한 경우 `409 SESSION_SUPERSEDED`로 끝나고 자신의 룸이 보상 삭제되며, 교체 세션은 영향받지 않는지 확인 (디스패치 시점에 두 번째 생성을 끼워 넣는 결정적 재현 테스트)
- 동시 생성 두 건의 응답이 {나중 쪽 성공 + 먼저 쪽 성공 또는 `SESSION_SUPERSEDED`} 중 하나로만 수렴하는지 확인 (동시성 통합 테스트 확장)
- 디스패치 실패(어댑터 예외·타임아웃·비정상 응답) 시 `500 SESSION_DISPATCH_FAILED`가 반환되고, **커밋된 신규 `PENDING`은 남으며**, 신규 룸에 보상 삭제가 시도되는지 확인 (S001과 동일 모델)
- 디스패치 실패로 잔존한 `PENDING`이 같은 유저의 재시도에서 자동 교체되어 정상 생성으로 수렴하는지 확인
- 토큰 발급 실패(`S001`) 시 디스패치가 호출되지 않는지 확인 (순서 계약)
- 룸 선생성 실패(`S002`)·검증 거부(400/403/404/409)·트랜잭션 실패 시 디스패치가 호출되지 않는지 확인
- 디스패치 실패 후에도 교체된 기존 세션의 룸 정리(best-effort)가 시도되는지 확인 (HBB1-18 "어떤 결과든 정리 시도" 계승)
- 디스패치 어댑터의 실패 로그·예외 메시지에 metadata 전문(`resumeContext` 포함)과 API Secret이 노출되지 않고, metadata의 UTF-8 바이트 수는 기록되는지 확인
- 수동 (실제 Cloud + 로컬 AI 워커): 세션 생성 시 `kkori-interviewer` 워커에 job이 도달하고 `parse_job_metadata`가 계약 필드를 파싱하는지, 이력서 없는 `FIVE_MIN` 세션에서도 입장하는지 확인
- 수동 (실제 Cloud) — 모호한 디스패치 잔여 위험의 실측, 두 갈래로 확인:
  - **워커 연결 상태**: 디스패치 실행 중 룸 삭제 → 에이전트 job이 종료되고 재실행되지 않는지 확인
  - **워커 미연결 상태**: 디스패치 생성 → `JS_PENDING` 확인(`lk dispatch list <룸 이름>`) → 룸 삭제 → 워커 연결 → job 할당·룸 재생성이 일어나지 않는지 확인. **이 갈래에서 뒤늦은 할당이 관찰되면 `listDispatch` 보상을 도입한다**(판정 기준 — 본문이 수용한 잔여 위험이 바로 이 경우다)

### 성능 요구사항

- 별도 SLA 없음 — LiveKit API 왕복이 1회(룸 생성) → 2회(+ 디스패치)로 늘며, 각 왕복은 `livekit.api-timeout`으로 상한된다(HBB1-18의 "SLA는 실측 후 정의" 유지).

### 인터페이스 요구사항

- 외부 시스템: LiveKit Cloud — Agent Dispatch Server API(`createDispatch`). 룸 생성·삭제와 동일 자격증명(`livekit.api-key`/`api-secret`)·엔드포인트를 사용한다.
- 프론트 계약: 변경 없음 — `POST /api/v1/sessions`의 요청·응답은 HBB1-18 그대로.
- 테스트 설정 계약: HBB1-18 계승 — 일반 테스트는 더미 설정으로 부팅하고 디스패치 어댑터는 스텁·모킹한다. 실제 Cloud 디스패치·워커 연동은 수동 검증한다.

### 제약사항

다음은 모두 **범위 밖**이며 후속 스토리에서 도입한다:

- webhook 수신·상태 전이(`PENDING → ACTIVE` 등) — 본 스토리의 세션은 디스패치 후에도 `PENDING`에 머무는 것이 정상이다
- 에이전트 이탈 복구(`AGENT_LOST` 재디스패치)·디스패치 상태 조회
- 면접 유형·직무별 질문 파이프라인 분기의 내용 — metadata 전달까지가 본 스토리, 해석·분기는 Kkori-AI 소관

### 기타 요구사항

- 디스패치 실패(`S004`) 로그에는 세션 id·룸 이름 등 식별자와 함께 **metadata의 UTF-8 바이트 수**를 기록한다 — 한글은 Java 문자 수와 전송 바이트 수가 달라, 한도(512KiB) 대비 진단에는 바이트 수(`getBytes(UTF_8).length`)가 유효하다. 크기는 개인정보가 아니면서, 반복 실패("같은 이력서로 재시도해도 계속 `S004`")의 payload 요인 여부를 로그만으로 배제·진단할 수 있게 한다. metadata 전문은 기록 금지(기능 1 기타 요구사항).

| S004 | SESSION_DISPATCH_FAILED | 500 | 에이전트 디스패치 실패·타임아웃·응답 검증 실패 (신설) |
