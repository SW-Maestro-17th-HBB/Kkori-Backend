# 계정 관리

> **User Story**: HBB1-10 — 나는 사용자로서 내 계정을 관리하기 위해 정보 조회·수정·탈퇴를 할 수 있다.
>
> **하위 이슈**: HBB1-53 [개발] 계정 설정/탈퇴 개발 · HBB1-245 [개발] 계정 복구·유예 만료 개발 · HBB1-246 [개발] 카카오 연결 해제 웹훅 개발

## Overview

본 기능은 로그인한 사용자가 자신의 계정 정보를 조회·수정하고 탈퇴하는 흐름, 그리고 탈퇴 계정의 복구를 정의한다. 모든 처리는 Spring API Server가 담당하며, 데이터는 PostgreSQL에 저장된다. 탈퇴는 **즉시 접근 차단(soft delete) + 유예 후 배치 파기**의 2단 구조로, 본 문서는 1단계(탈퇴 요청·파기 대기 등록)와 유예 기간 내 복구, 유예 초과 계정의 처리까지를 다룬다. 추가로 사용자가 카카오계정 관리 페이지에서 직접 연결을 끊는 경우를 동기화하는 **카카오 연결 해제 웹훅** 수신을 포함한다.

경계: 로그인 판정·토큰 계약은 소셜 로그인 스토리(HBB1-11)의 PRD를 따르고, 동의 항목 정의·동의 상태 조회는 수집 동의 스토리(HBB1-12), 유예 경과 후 실데이터 파기·카카오 연결 해제(unlink) 실행·`deletion_log` 상태 전환(`PURGED`/`FAILED`)은 영구 삭제 스토리의 PRD에서 다룬다. 단 파기 배치가 의존하는 `deletion_log` 테이블(스키마 포함)은 본 스토리에서 생성한다.

### 기능 요구사항

| No. | Function | Description |
| --- | --- | --- |
| 1 | 내 정보 조회 | 인증된 사용자의 계정 정보(id·email·name·createdAt)를 `GET /api/v1/user`로 반환해야 한다. |
| 2 | 내 정보 수정 | `PATCH /api/v1/user`로 name(1~100자)을 수정하고 수정된 계정 정보를 반환해야 한다. email·provider_id는 수정 불가. |
| 3 | 회원 탈퇴 | `DELETE /api/v1/user`에서 soft delete + RT 전체 폐기 + 동의 철회 append + 파기 대기 등록을 한 트랜잭션으로 수행하고 `purgeScheduledAt`을 반환해야 한다. |
| 4 | 계정 복구·유예 만료 처리 | 카카오 로그인 시 탈퇴 계정을 유예 기간 내면 재동의(`/auth/signup`)를 거쳐 복구하고, 유예 초과면 식별정보를 즉시 파기(provider_id 마스킹, email·name NULL)해 신규 유저로 흘려보내야 한다. |
| 5 | 카카오 연결 해제 웹훅 | 사용자가 서비스 외부에서 카카오 연결을 끊으면 카카오가 보내는 웹훅을 수신해 해당 계정을 탈퇴 처리해야 한다. |

## 내 정보 조회

### 설명

인증된 사용자가 `GET /api/v1/user`를 호출하면 서버는 AT의 userId로 계정을 조회해 반환해야 한다.

- 응답 필드는 `id`·`email`·`name`·`createdAt`으로 구성한다. `email`·`name`은 카카오 제공 여부에 따라 null일 수 있다(HBB1-11에서 nullable로 확정).
- `provider_id`(카카오 회원번호)는 내부 식별 정보이므로 응답에 포함하지 않는다.
- 탈퇴 유저 차단은 JWT 필터가 매 요청 `deleted_at` 검증으로 수행하므로(HBB1-11 구현) 본 API에 도달한 요청은 항상 활성 유저다. 단 `users`에 `@SQLRestriction`이 없으므로, 서비스 계층에서 userId 조회 시 방어적으로 `deleted_at IS NULL` 여부를 확인해 어긋나면 401로 처리한다.

### 실행 조건

- 유효한 Access Token으로 인증된 상태여야 한다.
- `users` 테이블에 해당 userId 레코드가 존재해야 한다.

### 검증 기준

- 유효한 AT로 호출 시 본인의 `id`·`email`·`name`·`createdAt`이 반환되는지 확인
- email 미제공 카카오 계정의 조회 시 `email: null`로 반환되는지 확인
- AT 없이 또는 무효한 AT로 호출 시 `401`이 반환되는지 확인
- 응답에 `provider_id`가 포함되지 않는지 확인

### 성능 요구사항

- 로컬 환경 기준 100ms 이내로 응답해야 한다.

### 인터페이스 요구사항

- 엔드포인트: `GET /api/v1/user` (인증 필요, `Authorization: Bearer {accessToken}`)
- 모든 응답은 공통 envelope `ApiResponse<T>`로 감싼다(HTTP 상태코드는 바디에 넣지 않음).

`GET /api/v1/user` 응답 예시:

```json
{
  "success": true,
  "data": {
    "id": 1,
    "email": "user@example.com",
    "name": "홍길동",
    "createdAt": "2026-01-15T09:00:00Z"
  }
}
```

### 제약사항

- 조회 대상은 본인 계정으로 한정한다. 타 유저 조회 API는 범위 외.

### 기타 요구사항

- 없음

## 내 정보 수정

### 설명

인증된 사용자가 `PATCH /api/v1/user`로 수정할 필드를 전달하면 서버는 검증 후 반영하고, 수정된 계정 정보(조회와 동일 형식)를 반환해야 한다.

- MVP에서 수정 가능한 필드는 `name` 하나다. `email`·`provider_id`는 카카오에서 온 식별 정보이므로 수정 불가.
- 요청 body의 미지원 필드(`email` 등)는 **거부하지 않고 무시**한다 — DTO에 정의된 필드만 바인딩하는 표준 JSON 역직렬화 관행을 따르며, 이후 필드가 추가돼도 구버전 서버가 신버전 클라이언트 요청을 깨뜨리지 않는다(전방 호환). 수정 불가 필드가 반영되지 않았음은 응답 body로 확인 가능하다.
- `name`은 앞뒤 공백 제거 후 1~100자여야 한다. 누락·null·공백뿐·길이 위반은 모두 `400 INVALID_NAME`으로 거부해야 한다.
- 길이는 **Unicode 코드 포인트 수** 기준으로 센다(`String.length()`의 UTF-16 단위 기준 금지). DB 제약인 `varchar(100)`이 코드 포인트 기준이므로 검증과 저장 제약이 1:1로 일치하며, 서로게이트 쌍 문자(이모지 등)가 2로 세어져 저장 가능한 이름을 거부하는 불일치를 방지한다.
- 검증은 서비스 계층에서 수행하고 도메인 에러 코드로 응답한다(bean validation의 공통 `C002`가 아님 — HBB1-11에서 확립한 기준: PRD에 도메인 에러 코드가 명시된 검증은 서비스 검증).
- 수정은 **user 행 잠금(비관적 잠금) 하에** 수행하고 잠금 후 활성 여부를 재확인해야 한다(탈퇴됐으면 401). 잠금 없이 조회 후 변경을 flush하면, 그 사이 커밋된 탈퇴(조건부 UPDATE)의 `deleted_at`을 조회 시점의 null 값으로 되덮어 **탈퇴가 취소되는 lost update**가 발생할 수 있다(Hibernate 기본 UPDATE는 전체 컬럼을 메모리 값으로 씀). 유저 상태를 쓰는 모든 경로(수정·탈퇴·토큰 재발급·로그인/복구)는 user 행 잠금을 직렬화 지점으로 공유하며 잠금 순서는 **user → deletion_log → RT**다(재발급·로그인 측 요구는 HBB1-11 PRD, 복구 측 절차는 기능 4 참조).

### 실행 조건

- 유효한 Access Token으로 인증된 상태여야 한다.

### 검증 기준

- 유효한 name으로 수정 시 DB에 반영되고 수정된 정보가 응답되는지 확인
- name 누락·null·공백뿐·101자 이상 요청이 `400 INVALID_NAME`으로 거부되고 DB가 변경되지 않는지 확인
- 앞뒤 공백이 제거되어 저장되는지 확인
- 경계값(1자·100자)이 허용되는지 확인
- `email` 등 미지원 필드가 포함된 요청에서 해당 필드는 무시되고 name만 반영되며, `email`이 변경되지 않는지 확인
- 서로게이트 쌍 문자가 포함된 name의 길이가 코드 포인트 기준으로 판정되는지 확인(예: BMP 밖 이모지 100개로 구성된 name은 허용 — UTF-16 단위로는 200)
- 수정 트랜잭션이 User를 읽은 뒤 탈퇴가 끼어들어도 계정이 되살아나지 않고 탈퇴 상태가 유지되는지 확인 (동시성 통합 테스트)
- 탈퇴된 유저의 수정 요청이 401로 거부되는지 확인
- AT 없이 호출 시 `401`이 반환되는지 확인

### 성능 요구사항

- 로컬 환경 기준 100ms 이내로 응답해야 한다.

### 인터페이스 요구사항

- 엔드포인트: `PATCH /api/v1/user` (인증 필요)

`PATCH /api/v1/user` 요청:

```json
{ "name": "새 이름" }
```

응답 `data`는 내 정보 조회와 동일 형식.

### 제약사항

- 수정 가능 필드는 `name`으로 한정한다. 필드 추가는 확장 범위.

### 기타 요구사항

- 없음

## 회원 탈퇴

### 설명

인증된 사용자가 `DELETE /api/v1/user`를 호출하면 서버는 아래 네 가지를 **한 트랜잭션**으로 수행하고, 파기 예정 시각을 반환해야 한다.

1. `users.deleted_at = now` (soft delete — 아래 직렬화 계약에 따라 `deleted_at IS NULL` 조건부 UPDATE 쿼리로 수행. `BaseEntity.softDelete()`는 영향 행 수 판정이 불가하므로 이 경로에는 사용하지 않음)
2. 해당 유저의 모든 Refresh Token에 `revoked_at = now` (`RefreshTokenRepository.revokeAllByUserId` 재사용. revoke-all로 폐기된 RT는 `replaced_by IS NULL`이므로 Grace Period 없이 재발급이 거부됨 — HBB1-11에서 검증된 동작)
3. `user_consent`: 탈퇴 시점에 최신 상태가 `AGREED`인 모든 동의 유형에 `WITHDRAWN`을 append (append-only, 해당 유형의 최신 `AGREED`와 동일한 version으로 기록)
4. `deletion_log` INSERT: `status = PENDING_PURGE`, `requested_at = now`, **`provider_id` 스냅샷 저장**

- **동일 유저의 탈퇴 처리는 직렬화해야 한다**: soft delete를 `deleted_at IS NULL` 조건부 UPDATE로 수행하고, **영향 행 수가 1인(상태 전이를 실제로 수행한) 트랜잭션만** 후속 작업(RT 폐기·`WITHDRAWN` append·`deletion_log` INSERT)을 진행한다. 영향 행 수가 0이면 이미 탈퇴된 것으로 보고 상태를 변경하지 않는다 — API 요청과 웹훅(기능 5)이 같은 유저에 동시 도착해도 `WITHDRAWN`·`deletion_log`가 중복 생성되지 않게 하기 위함이다. 조건부 UPDATE에서 밀린 API 요청은 기존 `deleted_at` 기준의 `purgeScheduledAt`을 반환한다(멱등).
- 응답의 `purgeScheduledAt`은 `deleted_at + 유예 기간`으로 계산한다. 유예 기간은 **3일**이며 설정값(`@ConfigurationProperties` record + compact constructor fail-fast — JwtProperties 패턴)으로 관리한다.
- `provider_id` 스냅샷은 파기 배치의 카카오 연결 해제(unlink, 어드민 키 방식) 호출에 필요하다. `users.provider_id`가 유예 만료 처리(기능 4)로 먼저 마스킹될 수 있으므로 탈퇴 시점에 확보해 둔다. 스냅샷도 개인 식별정보이므로 복구 시(CANCELLED 전환)와 파기 완료 시(unlink 후) NULL 처리한다 — 파기 시점 처리는 영구 삭제 스토리 범위.
- 탈퇴 직후부터 JWT 필터의 `deleted_at` 검증이 잔여 AT를 차단하므로(이미 구현됨) AT 블랙리스트는 불필요하다.
- 실데이터(이력서·세션 로그·리포트 등) 파기와 카카오 unlink 호출은 유예 경과 후 파기 배치가 수행한다(영구 삭제 스토리 범위). 본 API는 파기 대기 등록까지만 책임진다.

### 실행 조건

- 유효한 Access Token으로 인증된 상태여야 한다.
- `deletion_log` 테이블이 존재해야 한다. 본 스토리에서 생성하며 스키마는 draft ERD에 `provider_id` 컬럼을 추가한 형태다.
  - **컬럼**: `id`(PK) · `user_id`(NOT NULL — FK 없이 애플리케이션이 무결성 관리, `refresh_token`과 동일 방침) · `provider_id`(nullable — 탈퇴 시 스냅샷, 복구·파기 완료 시 NULL) · `requested_at`(NOT NULL) · `purged_at`(nullable — 파기 완료 시각) · `status`(NOT NULL — PENDING_PURGE/PURGING/PURGED/FAILED/CANCELLED) · `purge_detail`(jsonb, nullable) · `updated_at`(NOT NULL — 마지막 상태 전이 시각. INSERT 시 `requested_at`과 동일 값으로 시작하고 상태 전이 시 갱신한다. 상태 전이는 조건부 UPDATE(벌크 쿼리)로 수행되어 auditing이 적용되지 않으므로 쿼리에서 명시적으로 갱신해야 한다. 용도: stale `PURGING` 회수·`FAILED` 재시도 판정 — 영구 삭제 스토리)
  - **인덱스**: 부분 UNIQUE 인덱스 `ux_deletion_log_active_user` — `(user_id) WHERE status IN ('PENDING_PURGE', 'PURGING', 'FAILED')` — 는 **영구 삭제 스토리에서 마이그레이션 도구와 함께 후속 도입**한다. JPA 애너테이션으로 표현할 수 없어 본 스토리에서는 생성하지 않으며, 그때까지 유저당 활성 삭제 요청 1건의 보장은 애플리케이션 직렬화 계약(조건부 UPDATE)이 단독으로 담당한다. `(status, requested_at)` 인덱스도 활성 레코드가 항상 소량이라 동일하게 측정 후 검토한다.
  - **상태 전이**: `PENDING_PURGE → CANCELLED`(복구 — 본 스토리, 조건부 전환) · `PENDING_PURGE·FAILED → PURGING`(파기 선점 — 영구 삭제 스토리, 조건부 전환. 복구와의 상호 배타는 기능 4 참조) · `PURGING → PURGED`(파기 성공) · `PURGING → FAILED`(파기 실패, 재시도 대상). `PURGED`·`CANCELLED`는 종결 상태로 재전이가 없다. `FAILED → CANCELLED` 전이는 존재하지 않는다 — FAILED는 유예 경과 후 파기 시도에서만 발생하고, 유예 초과 계정은 복구가 불가하기 때문(기능 4). 중단으로 방치된 `PURGING`의 회수(stale 판정·재시도)는 영구 삭제 스토리에서 정의한다.

### 검증 기준

- 탈퇴 시 `deleted_at`·RT 전체 폐기·`WITHDRAWN` append·`deletion_log` INSERT(PENDING_PURGE, provider_id 스냅샷 포함)가 모두 반영되는지 확인
- 트랜잭션 중단 시 네 가지가 모두 롤백되는지 확인
- 응답의 `purgeScheduledAt`이 탈퇴 시각 + 3일인지 확인
- 탈퇴 직후 잔여 AT로 인증 필요 API 호출 시 `401`이 반환되는지 확인
- 탈퇴로 폐기된 RT로 재발급 시도 시 Grace Period 없이 거부되는지 확인
- 탈퇴 시점에 `WITHDRAWN` 상태였던 동의 유형(예: marketing 미동의)에는 중복 `WITHDRAWN`이 append되지 않는지 확인
- 동일 유저의 탈퇴 처리 두 건이 **동시에** 실행돼도 상태 전이를 수행한 한 건만 후속 작업을 진행해 `WITHDRAWN` append와 `deletion_log` INSERT가 각 1건만 생성되는지 확인 (동시성 통합 테스트)

### 성능 요구사항

- 로컬 환경 기준 100ms 이내로 응답해야 한다.

### 인터페이스 요구사항

- 엔드포인트: `DELETE /api/v1/user` (인증 필요, 요청 body 없음)
- 환경 변수/설정: 탈퇴 유예 기간(기본 3일)

`DELETE /api/v1/user` 응답 예시:

```json
{
  "success": true,
  "data": {
    "purgeScheduledAt": "2026-01-18T09:00:00Z"
  }
}
```

### 제약사항

- 즉시 물리 삭제는 지원하지 않는다. 파기는 유예 후 배치로만 수행한다.
- 유예 기간 단축·즉시 파기 요청은 MVP 범위 외.

### 기타 요구사항

- 프론트는 탈퇴 응답 수신 후 로컬 토큰을 삭제하고, `purgeScheduledAt` 이전에 재로그인해 재동의하면 계정이 복구됨을 안내할 수 있다.

## 계정 복구·유예 만료 처리

### 설명

카카오 로그인(`POST /api/v1/auth/kakao`, HBB1-11)에서 `provider_id`가 존재하고 `deleted_at`이 기록된 유저로 판정되면, 서버는 유예 기간 경과 여부(`now < deleted_at + 유예 기간`)와 **해당 유저 최신 `deletion_log`의 상태**로 분기해야 한다(최신 = `requested_at`·`id` 내림차순 정렬 명시 조회). 판정·응답 계약은 HBB1-11 PRD(본 변경으로 개정), 내부 처리는 본 문서가 정의한다(현재 구현 `TokenService.processKakaoLogin`은 기간 검증 없이 로그인 시점에 즉시 `deleted_at`을 해제하므로 본 요구사항으로 교체).

| 최신 로그 상태 | 처리 (`/auth/kakao` 판정·`/auth/signup` 재판정 공통) |
| --- | --- |
| `PENDING_PURGE` + 유예 내 | 재동의를 거쳐 복구 (아래) |
| `PENDING_PURGE` + 유예 초과 | 해당 탈퇴 건에 **바인딩된** signup token 발급(`isNewUser: true`, **계정 미변경**) — 식별정보 파기와 신규 생성은 제출 시점에 수행 (아래) |
| `PURGING`·`FAILED` | **`409 PURGE_IN_PROGRESS`(U002)로 차단** — 파기 배치가 스냅샷으로 unlink를 수행·재시도할 소유권을 쥔 상태라, 신규 가입을 허용하면 방금 만든 카카오 연결이 배치의 unlink로 끊기는 경합이 생긴다. FAILED 차단의 함의로 파기 성공 전까지 해당 카카오 계정은 가입이 불가하다 — 운영 개입(파기 실패 해소)이 필요한 잔여 리스크로 수용 |
| 로그 부재·종결 상태 모순 | 엔드포인트별로 다르다: `/auth/kakao`는 ERROR 로그 + **식별정보 즉시 파기** 후 신규 취급(활성 로그가 없어 바인딩 대상도 배치 경합도 없음 — 가용성 우선), `/auth/signup`은 `401 INVALID_SIGNUP_TOKEN`(이미 사용된 토큰 — 정보 비노출) |

에러 구분 원칙: **401은 토큰이 더 이상 유효한 대상을 가리키지 않을 때, 409는 대상은 유효하나 파기가 진행 중일 때** 사용한다.

상태 판정과 후속 상태 변경(식별정보 파기·복구)은 **user 행 잠금에 이어 대상 `deletion_log` 행 잠금을 획득한 뒤** 수행해야 한다(잠금 순서 user → deletion_log — 기능 2의 직렬화 계약). 로그를 잠금 없이 읽으면 판정 직후 파기 배치가 `PURGING`으로 선점해도 마스킹·신규 발급이 계속 진행되어 409 계약이 깨진다. 상태 재조회는 잠금 획득 후 스칼라 쿼리로만 한다(선조회 엔티티는 1차 캐시 때문에 재확인이 되지 않음).

**유예 기간 내 — 재동의를 거쳐 복구**:

복구는 재로그인만으로 자동 수행하지 않는다. 탈퇴로 동의가 철회된 상태이므로 유저가 동의를 다시 제출해야 복구가 성립한다.

1. `/auth/kakao`: 계정을 변경하지 않고 **복구용 signup token**을 발급하며 `isNewUser: false`·`isRestored: true`로 응답한다. 복구용 토큰은 신규 가입용과 claim 구성이 같되 **`deletion_log_id`(해당 유저의 활성 `PENDING_PURGE` 레코드 id) claim을 추가**해 특정 탈퇴 요청 건에 바인딩한다. 프론트는 신규 가입과 같은 동의 화면으로 라우팅하되 복구 안내를 표시할 수 있다.
2. `/auth/signup` 제출 시 토큰에 `deletion_log_id`가 있으면 복구 경로로 처리하고, 아래를 **한 트랜잭션에서 이 순서대로** 수행한다:
   1. Clock에서 트랜잭션 시각 `now`를 한 번 취득한다
   2. `deletion_log_id`로 레코드를 조회해 **1차 신원 검증**한다 — 레코드가 없거나 토큰의 `provider_id`와 스냅샷이 일치하지 않으면 `401 INVALID_SIGNUP_TOKEN`. 판정 재료 중 `requested_at`·`user_id`는 불변이지만 **`provider_id` 스냅샷은 CANCELLED/PURGED 전환 시 NULL로 바뀌는 가변 값**이므로, 선조회 이후의 상태 전이는 4의 재확인이 검출한다
   3. 레코드의 `user_id`로 **user 행을 잠그고, 이어서 대상 `deletion_log` 행을 잠근다** (잠금 순서 user → deletion_log → RT — 기능 2의 직렬화 계약. 로그 행 잠금이 판정과 후속 상태 변경 사이에 배치의 `PURGING` 선점이 끼어드는 것을 차단한다)
   4. 잠금 획득 후 **로그 상태를 스칼라 쿼리로 재확인**한다(엔티티 재조회는 1차 캐시가 낡은 인스턴스를 반환해 재확인이 되지 않음) — 위 상태별 정책 표대로 분기: `PENDING_PURGE`+유예 내(`now < requested_at + 유예 기간`, 시각 정합 요구에 의해 `deleted_at` 기준과 동일)면 5로 진행, `PENDING_PURGE`+유예 초과면 유예 초과 처리(식별정보 파기 후 신규 계정 생성), `PURGING`·`FAILED`면 `409 PURGE_IN_PROGRESS`, 종결 상태·레코드 소실이면 `401 INVALID_SIGNUP_TOKEN`
   5. `id = {deletion_log_id} AND status = 'PENDING_PURGE' AND requested_at + 유예 기간 > {now}` **조건부 UPDATE**로 `CANCELLED` 전환 + `provider_id` 스냅샷 NULL 처리 (배치 파기 대상에서 제외, 탈퇴 요청 이력은 audit으로 보존). 유예 조건을 UPDATE 술어에도 중복 포함해, 판정 순서를 착오한 구현이 유예 초과 건을 취소하는 실수를 쿼리 수준에서 차단한다. **영향 행 수가 1인 경우에만 복구를 계속 진행**하며, 0이면 `401` — 모든 복구 제출이 user 잠금을 먼저 잡아 동시 제출은 4에서 걸러지므로, 0행은 재확인 이후의 예외적 상태 변화를 방어적으로 감지하는 최후 방어선이다
   6. `users.deleted_at = NULL` (잠금 보유 중)
   7. `user_consent`: 제출받은 동의 내역을 append (신규 가입과 동일한 필수 동의 검증 — 누락 시 `400 MISSING_REQUIRED_CONSENT` — 및 동일한 저장 방식, **최신 동의서 버전**으로 기록)
   8. JWT 발급
3. 동의 화면에서 이탈(미제출)하면 계정은 탈퇴 상태를 유지하고 파기 일정도 그대로 진행된다 — 복구는 명시적 재동의로만 성립한다.

- **토큰 용도 분리**: `deletion_log_id`가 없는(신규 가입용) 토큰으로 제출했는데 `provider_id`가 탈퇴 상태 계정이면 복구하지 않고 `401 INVALID_SIGNUP_TOKEN`으로 거부한다 — 프론트는 재로그인(`/auth/kakao`)으로 새 복구용 토큰을 받게 한다.
- `deletion_log_id` 바인딩이 필요한 이유: signup token은 무저장이라 개별 무효화가 불가능하고 탈퇴의 RT 전량 폐기로도 끊기지 않는다. 바인딩이 없으면 "토큰 발급 → 복구(또는 가입) → 재탈퇴" 후 10분 내 같은 토큰을 재사용해 **최신 탈퇴까지 되돌리고 JWT를 획득**할 수 있다. 바인딩과 조건부 전환으로 토큰 하나는 정확히 한 탈퇴 건만, 한 번만 복구할 수 있다.

- 복구는 기존 계정 데이터(id·name·email·가입 시각)를 유지한다. signup token의 `email`·`nickname` claim은 복구 경로에서 사용하지 않는다.
- 탈퇴로 철회된 동의를 시스템이 복원하지 않고 다시 받는 이유: 유저가 철회한 동의를 시스템이 임의로 재기록하지 않는다(명시적 동의 원칙). 탈퇴~복구 사이 동의서 버전이 갱신된 경우에도 자연스럽게 최신 버전으로 동의받으며, "무엇을 복원할지" 판별(이력 시각 추론이나 스냅샷)이 아예 필요 없어진다.
- signup token 유효기간(10분) 내에 유예가 만료되는 엣지는 위 3번의 제출 시점 유예 재판정이 흡수한다 — 제출 시점에 유예가 지났으면 유예 초과 처리(식별정보 파기)를 수행한 뒤 신규 계정을 생성한다.

**유예 기간 초과 (배치 지연·실패로 미파기)** — 바인딩 토큰 발급 후 제출 시점에 파기·신규 생성:

1. `/auth/kakao` 판정 시: **계정을 변경하지 않고** 해당 `PENDING_PURGE` 건에 바인딩된(`deletion_log_id` claim 포함) signup token을 발급하며 `isNewUser: true`로 응답한다. 이 시점에 식별정보를 파기하지 않는 이유: 파기(마스킹)하면 제출 전 재로그인이 `provider_id` 매칭에 실패해 **아무 바인딩 없는 완전 신규로 판정**되어, 그 사이 배치가 선점(`PURGING`)해도 409 차단을 우회하는 창이 생긴다. 계정을 남겨두면 재로그인은 항상 이 판정을 다시 탄다
2. `/auth/signup` 제출 시(복구 절차의 유예 초과 분기 — user·로그 행 잠금 하에 재판정 후): `users`의 식별정보를 파기하고(`email`·`name` NULL, `provider_id`는 **`PURGED_{users.id}` 형식으로 마스킹**) **같은 트랜잭션에서** 제출된 동의로 신규 계정을 생성한다. 마스킹 값은 실제 카카오 회원번호(숫자)와 형식상 겹치지 않으므로 UNIQUE 충돌이 발생하지 않는다
3. `deletion_log`는 `PENDING_PURGE` 그대로 둔다 — 잔여 실데이터 파기와 unlink는 배치가 스냅샷 기반으로 계속 책임진다

- `provider_id`를 NULL이 아닌 마스킹으로 파기하는 이유: 컬럼의 NOT NULL 제약과 "모든 유저는 provider_id를 가진다"는 도메인 불변식을 유지해 엔티티 변경·마이그레이션 없이 처리하기 위함이다. 마스킹 형식은 (1) 원본 복원이 불가능하고(해시 금지 — 카카오 회원번호는 숫자라 전수 대입으로 역산 가능), (2) `users.id` 기반이라 UNIQUE 제약 하에서 유일하며, (3) 재실행해도 같은 값이라 멱등하다. 파기 배치의 식별정보 파기도 동일 규칙을 따라야 한다(영구 삭제 스토리에 위임하는 요구사항).

- 유예 초과 경로에 별도 에러 코드는 두지 않는다. 사용자 관점에서는 파기 완료된 계정과 동일하게 신규 가입으로 흘러가며, 고지한 유예 정책("3일 내 재로그인 시 복구")과 동작이 일치한다.
- **복구와 파기 배치의 상호 배타**: 파기 배치는 파기 작업을 시작하기 전에 대상 레코드를 `PENDING_PURGE·FAILED → PURGING` **조건부 전이로 선점**해야 한다(영구 삭제 스토리에 위임하는 요구사항). 복구의 조건부 `CANCELLED` 전환과 배치의 선점이 같은 `status`를 놓고 경쟁하므로 정확히 하나만 성립한다 — 선점된(`PURGING`) 레코드의 복구 제출은 조건부 전환 실패로 401이 되고, 먼저 `CANCELLED`된 레코드는 배치가 선점하지 못한다. 식별정보 파기(마스킹·NULL) 자체는 멱등이므로 유예 초과 로그인 처리와 배치가 중복 수행해도 무해하다.

### 실행 조건

- HBB1-11의 카카오 로그인 판정 흐름이 구현되어 있어야 한다.
- 탈퇴 유예 기간 설정값이 로드되어 있어야 한다.

### 검증 기준

- 유예 기간 내 탈퇴 유저가 로그인하면 계정 변경 없이 `isNewUser: false`·`isRestored: true`·signupToken이 반환되고, AT·RT는 반환되지 않는지 확인
- 복구 대상의 `/auth/signup` 제출 시 `deleted_at` 해제·`CANCELLED` 전환(스냅샷 NULL 포함)·제출 동의 append·JWT 발급이 한 트랜잭션으로 반영되는지 확인
- 복구 signup에서 필수 동의 누락 시 `400 MISSING_REQUIRED_CONSENT`가 반환되고 계정이 탈퇴 상태로 유지되는지 확인
- 동의 미제출로 이탈한 탈퇴 계정은 상태 변화 없이 `PENDING_PURGE`가 유지되어 파기 대상으로 남는지 확인
- 복구 트랜잭션 중단 시 전부 롤백되는지 확인
- 복구 후 `deletion_log`의 `CANCELLED` 레코드가 배치 스캔 대상(`PENDING_PURGE`·`FAILED`)에서 제외되는지 확인
- 복구된 유저가 정상적으로 인증 필요 API를 사용할 수 있는지 확인
- 복구 시 기존 계정의 `id`·`name`·`email`·가입 시각이 유지되는지 확인
- 복구로 append된 동의가 제출 내역 그대로·최신 동의서 버전으로 기록되는지 확인
- signup token 발급 후 제출 시점에 유예가 만료된 경우, 복구가 아닌 식별정보 파기 + 신규 계정 생성으로 처리되는지 확인
- 복구에 이미 사용된 복구용 토큰을 재사용하면(복구 후 재탈퇴한 경우 포함) 조건부 전환 실패로 `401 INVALID_SIGNUP_TOKEN`이 반환되고 계정이 복구되지 않는지 확인
- 신규 가입용(`deletion_log_id` 없는) 토큰으로 탈퇴 상태 계정에 제출 시 복구되지 않고 `401 INVALID_SIGNUP_TOKEN`이 반환되는지 확인
- 동일 복구용 토큰의 동시 제출 두 건 중 한 건만 복구를 수행하는지 확인 (동시성 통합 테스트)
- 파기 배치가 선점한(`PURGING`) 레코드에 대한 복구 제출이 상태 재확인에서 `409 PURGE_IN_PROGRESS`로 차단되는지 확인 (배치 구현 전이므로 상태를 직접 설정해 검증)
- `PURGING`·`FAILED` 상태 계정의 카카오 로그인이 `409 PURGE_IN_PROGRESS`로 차단되는지 확인
- 유예 만료 판정과 배치의 `PURGING` 선점이 **동시에** 실행돼도, 선점이 먼저 커밋되면 409로 차단되고 식별정보가 파기되지 않는지 확인 (동시성 통합 테스트 — 로그인·복구 제출 양 경로)
- 탈퇴 상태(`deleted_at` 기록)인데 로그가 없거나 종결 상태인 모순 계정의 로그인은 ERROR 로그를 남기고 신규 전환되는지 확인
- 유예 초과 상태에서 복구용 토큰을 제출하면 `deletion_log`가 `CANCELLED`로 전환되지 않고 `PENDING_PURGE`를 유지한 채 신규 계정이 생성되는지 확인
- **유예 기간(3일) 초과** 유저가 로그인하면 복구되지 않고 `isNewUser: true` + 해당 탈퇴 건에 바인딩된 signupToken이 반환되며, **계정은 변경되지 않는지** 확인
- 유예 만료 토큰 제출 시 식별정보 파기(`email`·`name` NULL, `provider_id` `PURGED_{users.id}` 마스킹)와 신규 계정 생성이 한 트랜잭션으로 수행되는지 확인
- **만료 로그인 → 배치 `PURGING` 선점 → 제출** 순서에서 제출이 `409 PURGE_IN_PROGRESS`로 차단되고 계정이 변경되지 않는지 확인 (통합 테스트)
- 유예 초과 후 동일 카카오 계정으로 가입 완료 시 `409 ALREADY_REGISTERED` 없이 새 계정이 생성되는지 확인
- 유예 만료 경계 시각(`deleted_at + 유예 기간` 정각)의 로그인은 복구가 아닌 유예 초과로 처리되는지 확인 (판정식 `now < deleted_at + 유예 기간`, Clock 고정 테스트)
- 유예 초과 처리 후에도 기존 `deletion_log`가 `PENDING_PURGE`로 유지되고 `provider_id` 스냅샷이 남아 있는지 확인

### 성능 요구사항

- HBB1-11의 `/auth/kakao` 성능 요구사항(로컬 100ms, 카카오 왕복 제외)을 그대로 따른다.

### 인터페이스 요구사항

- 별도 엔드포인트 없음 — `POST /api/v1/auth/kakao`(판정·signup token 발급)와 `POST /api/v1/auth/signup`(복구 실행)의 내부 분기. 응답 계약(`isRestored`, signupToken)은 HBB1-11 PRD(본 변경으로 개정된 oauth.md)를 따른다.
- 환경 변수/설정: 탈퇴 유예 기간(회원 탈퇴 기능과 공유)

### 제약사항

- 유예 기간은 3일로 고정하되 설정으로 조정 가능해야 한다(코드 상수 금지).
- 복구는 유예 기간 내 재로그인 + 재동의 제출로만 가능하다. 재로그인만으로는 복구되지 않으며, 별도 복구 API는 두지 않는다.
- 유예 초과·미파기 계정의 복구는 지원하지 않는다(식별정보 선행 파기로 신규 전환).

### 기타 요구사항

- 유예 초과로 재가입한 유저의 옛 `deletion_log`를 배치가 나중에 unlink 처리하면 동일 카카오 계정의 새 연결이 끊길 수 있다. 이 경우 재로그인 시 카카오 동의 화면이 다시 뜰 뿐 데이터 유실은 없으나, 파기 배치는 **unlink 전 동일 `provider_id`의 활성 계정 존재 시 unlink를 생략**해야 한다(영구 삭제 스토리에 위임하는 요구사항).

## 카카오 연결 해제 웹훅

### 설명

사용자가 서비스 외부(카카오계정 관리 페이지 등)에서 앱과의 연결을 끊으면 서비스는 이를 인지할 수 없으므로, 카카오가 보내는 **연결 해제 웹훅**을 수신해 해당 계정을 탈퇴 처리로 동기화해야 한다. (카카오 문서 기준: 웹훅은 서비스 외부에서 연결이 끊긴 경우에만 발송되며, 서비스가 어드민 키로 unlink API를 호출한 경우에는 발송되지 않으므로 파기 배치의 unlink와 루프가 생기지 않는다.)

- 카카오는 GET 또는 POST로 웹훅을 전송하므로 **두 메서드 모두** 수신해야 한다.
- 검증: `Authorization: KakaoAK {대표 어드민 키}` 헤더가 서버 설정의 어드민 키와 일치하고 `app_id`가 우리 앱 ID와 일치할 때만 탈퇴 동기화를 수행한다. 불일치 시 **상태 변경 없이 보안 로그(WARN 이상, 수신 파라미터 포함)만 남기고 동일하게 `200 OK`를 반환한다** — 카카오는 200 외 응답을 실패로 간주해 재전송하며 연속 실패 시 웹훅을 비활성화하므로, 401 등 에러 응답은 사용하지 않는다(카카오 웹훅 명세). 검증 실패 탐지는 내부 모니터링(로그 기반)이 담당한다.
- 처리: `user_id`(카카오 회원번호)로 활성 유저(`provider_id` 일치 + `deleted_at IS NULL`)를 조회한다.
  - **활성 유저 존재**: 회원 탈퇴(기능 3)와 동일한 트랜잭션(soft delete + RT 전체 폐기 + WITHDRAWN append + deletion_log INSERT)을 수행한다. 기능 3의 **직렬화 계약**(`deleted_at IS NULL` 조건부 UPDATE, 상태 전이를 실제로 수행한 트랜잭션만 후속 작업 진행)을 그대로 따른다.
  - **미존재·이미 탈퇴**: 아무것도 하지 않는다. 동일 요청이 중복 수신될 가능성에 대비해 웹훅 처리는 **멱등**이어야 한다. 순차 중복 수신은 활성 유저 조회 실패로, 동시 중복·API 탈퇴와의 경합은 조건부 UPDATE의 영향 행 수 0으로 흡수된다.
- 검증·처리의 성공 여부와 무관하게 모든 웹훅 요청에 `200 OK`를 **3초 이내** 반환해야 한다(카카오 요건. 무응답·높은 오류 빈도가 지속되면 웹훅이 비활성화될 수 있음).
- 연결 해제 웹훅에는 **재전송이 지원되지 않는다**(카카오의 단계별 재전송은 계정 상태 변경 웹훅 전용). 따라서 처리 실패를 카카오 재전송으로 복구할 수 없으며, 탈퇴 동기화 처리 중 오류는 에러 로그(ERROR 레벨, `user_id` 포함)로 남겨 내부 모니터링으로 탐지한다.
- `referrer_type`(ACCOUNT_DELETE·UNLINK_FROM_APPS 등)은 처리 분기 없이 로그로만 기록한다. `INCOMPLETE_SIGN_UP`은 우리 쪽 계정이 없으므로 미존재 경로로 자연 흡수된다.
- 웹훅으로 탈퇴된 유저가 유예 기간 내 다시 카카오 로그인하면 카카오 재연결(동의 화면) 후 동일 회원번호로 code가 발급되므로, 기능 4의 복구 흐름이 그대로 적용된다.

### 실행 조건

- 카카오 개발자 콘솔 [앱] > [웹훅] > [연결 해제 웹훅]에 웹훅 URL이 등록되어 있어야 한다(외부에서 접근 가능한 배포 환경 필요 — 로컬 개발 단계에선 통합 테스트로 대체).
- 카카오 어드민 키가 서버 환경 변수로 설정되어 있어야 한다.
- 웹훅 엔드포인트가 SecurityConfig에서 JWT 인증 예외 경로로 등록되어 있어야 한다(어드민 키로 자체 검증).

### 검증 기준

- 올바른 어드민 키 헤더 + 활성 유저의 `user_id`로 웹훅 수신 시 탈퇴 트랜잭션(기능 3과 동일 4종)이 수행되고 200이 반환되는지 확인
- GET·POST 두 메서드 모두 동일하게 처리되는지 확인
- 어드민 키 불일치 또는 `app_id` 불일치 시에도 200이 반환되되, 어떤 유저도 변경되지 않고 보안 로그(WARN 이상)가 남는지 확인
- 이미 탈퇴한 유저·존재하지 않는 `user_id`의 웹훅에 200이 반환되고 상태 변화가 없는지(멱등) 확인
- 동일 웹훅이 중복 수신되어도 `deletion_log`가 중복 INSERT되지 않는지 확인
- 탈퇴 동기화 처리 중 오류 발생 시 에러 로그가 남는지 확인
- 동일 유저의 웹훅 두 건이 **동시에** 처리되거나 웹훅과 `DELETE /api/v1/user`가 경합해도 탈퇴 트랜잭션이 한 번만 수행되는지(`WITHDRAWN`·`deletion_log` 각 1건) 확인 (동시성 통합 테스트)
- `referrer_type`이 로그에 기록되는지 확인

### 성능 요구사항

- 200 응답을 3초 이내 반환해야 한다(카카오 요건). 로컬 기준 100ms 이내 목표.

### 인터페이스 요구사항

- 엔드포인트: `GET·POST /api/v1/webhook/kakao/unlink` (JWT 인증 불필요, 어드민 키 헤더로 검증)
- 수신 헤더: `Authorization: KakaoAK {대표 어드민 키}`
- 수신 파라미터: `app_id`(앱 ID) · `user_id`(연결 끊은 사용자의 회원번호) · `referrer_type`(끊기 경로)
- 환경 변수: 카카오 대표 어드민 키(`KAKAO_ADMIN_KEY`), 앱 ID — `@ConfigurationProperties` record + fail-fast 패턴(KakaoOAuthProperties 참조)
- 외부 설정: 카카오 개발자 콘솔 [앱] > [웹훅] > [연결 해제 웹훅] URL 등록

### 제약사항

- 웹훅 수신·검증·탈퇴 동기화까지만 다룬다. 계정 상태 변경 웹훅(보안 이벤트 토큰) 등 다른 웹훅 유형은 범위 외.
- **[MVP 잔여 위험]** 연결 해제 웹훅은 재전송이 없어 단 한 번의 수신·처리 실패로도 유실될 수 있다. 유실 시 유저가 서비스 외부에서 표시한 연결 해제 의사가 반영되지 않아, **계정과 기존 AT·RT가 활성 상태로 유지되고 개인정보 파기가 시작되지 않는다**. MVP의 대응은 아래로 한정하고 나머지는 명시적 잔여 위험으로 수용한다.
  - **수신 후 처리 실패**: ERROR 로그(`user_id` 포함)로 탐지해 수동 조치한다(기타 요구사항의 운영 절차).
  - **수신 자체가 안 된 유실**(서버 다운·네트워크 오류): 서버에 흔적이 남지 않아 MVP에서는 탐지 불가하다. 카카오 '연결된 사용자 목록 조회 API'(어드민 키)로 카카오 측 연결 회원번호와 서비스 활성 유저를 대조하는 **정기 대사 배치를 후속 범위**로 둔다.
  - 완화 요인: 해당 유저가 재로그인하면 카카오 재연결(재동의)을 거쳐 관계가 재성립되므로, 위험은 "연결을 끊고 돌아오지 않는 유저"의 계정·데이터 보관이 지속되는 경우에 국한된다.

### 기타 요구사항

- 어드민 키는 unlink 호출(영구 삭제 스토리)에도 사용되므로 환경 변수 도입은 본 스토리에서 수행한다.
- 운영 절차: 웹훅 처리 실패 ERROR 로그가 확인되면 백엔드 담당자가 해당 유저를 수동으로 탈퇴 처리한다(기능 3과 동일한 상태 변경 — soft delete·RT 폐기·WITHDRAWN append·deletion_log 기록 — 을 운영 작업으로 수행).

## 공통: 시각 처리

- 모든 시각은 **UTC 기준의 절대 시점**으로 저장·계산하며, 도메인 시각 타입은 **`Instant`로 통일**한다. auth 도메인(`refresh_token`·JWT)은 이미 Instant를 사용 중이고, `BaseEntity`(`created_at`·`updated_at`·`deleted_at`)와 `user_consent.created_at`의 `LocalDateTime`은 본 스토리에서 Instant로 전환한다(서버 타임존에 따라 유예 계산이 달라지는 문제 제거).
- API 응답의 시각 필드(`createdAt`·`purgeScheduledAt` 등)는 ISO-8601 UTC(`Z` 접미, 예: `2026-01-18T09:00:00Z`)로 직렬화한다.
- 시각 취득은 주입된 `Clock`을 사용한다(`Instant.now()` 직접 호출 금지). `BaseEntity.softDelete()`처럼 내부에서 시스템 시간을 직접 취하는 메서드는 시각을 파라미터로 받도록 변경한다. 유예 만료·복구 경계 등 시간 조건 테스트는 Clock 고정으로 검증한다.
- 탈퇴 트랜잭션(기능 3·5)은 Clock에서 시각을 **한 번만** 취해 `deleted_at`·`deletion_log.requested_at`·`WITHDRAWN`의 `created_at`에 동일 값을 사용한다(한 트랜잭션이 남기는 기록 간 시각 정합 — `purgeScheduledAt` 계산·audit 일관성).
