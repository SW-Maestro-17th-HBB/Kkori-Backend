# 수집 동의

> **User Story**: HBB1-12 — 나는 사용자로서 음성·자료 활용에 동의하기 위해 수집 동의를 할 수 있다.
>
> **하위 이슈**: (지라 하위 이슈 생성 후 기입)

## Overview

본 기능은 서비스가 수집·활용하는 데이터에 대한 사용자 동의의 **항목·동의서 버전·저장 정책**을 확정하고, 동의 검증 메타데이터의 원천인 **현재 동의 항목·버전 제공**, 가입 후 **동의 상태 조회**와 **선택 동의 변경** API를 제공한다. 모든 처리는 Spring API Server가 담당하며, 동의 이력은 PostgreSQL `user_consent` 테이블에 저장된다. 동의 기록의 핵심 불변식은 **기록된 버전 = 사용자가 실제 확인한 동의서의 버전**이다 — 이를 보장하는 버전 확인 계약(확인한 버전 제출·서버 대조, 불일치 시 409)을 기능 1이 정의하며, 이에 따라 `/auth/signup` 요청 계약(consents 항목의 `version` 필드)이 개정된다(oauth.md 함께 개정).

동의 수집의 진입점 자체는 앞선 두 스토리에 이미 구현되어 있다. 가입·복구 시 동의 제출(`POST /api/v1/auth/signup`)과 필수 동의 검증의 계약은 소셜 로그인 스토리(HBB1-11, oauth.md)가, 탈퇴 시 동의 철회(`WITHDRAWN` append)와 유저 상태 쓰기의 직렬화 계약은 계정 관리 스토리(HBB1-10, account.md)가 소유한다. 두 PRD가 "동의 항목의 정의·변경 및 저장 정책은 수집 동의 스토리(HBB1-12)를 따른다"로 위임한 부분 — 항목 정의, 동의서 버전 관리, append-only 저장 계약 — 을 본 문서가 정의하며, 현재 코드 상수로 고정된 동의서 버전(`CONSENT_VERSION = 1`)을 본 스토리에서 설정 기반 정책으로 교체한다.

경계: 동의서 문서 본문의 작성·게시는 서버 범위 외다(프론트 정적 문서·운영 소유, 서버는 어떤 버전에 동의했는지만 기록). 동의서 버전 갱신 시 기존 유저에게 재동의를 요구하는 흐름(로그인 시 감지 → 재동의 화면)은 확장 범위로, 실제 개정이 발생할 때 설계한다. 동의 이력의 보존 기간·파기 시점·비식별화 정책은 본 스토리에서 확정하지 않고, 영구 삭제 스토리에서 법무·개인정보 담당 확인을 거쳐 확정한다(아래 저장 정책 참조).

### 기능 요구사항

| No. | Function | Description |
| --- | --- | --- |
| 1 | 동의 항목·버전·저장 정책 | 동의 항목 4종(필수 `privacy`·`audio_usage`·`resume_usage`, 선택 `marketing`)과 항목별 동의서 버전(설정 관리), 버전 확인 계약(확인 버전 제출·대조, 불일치 409), append-only 저장 계약을 정의해야 한다. |
| 2 | 현재 동의 항목·버전 제공 | `GET /api/v1/consents`로 동의 화면 구성에 필요한 항목·필수 여부·현재 버전을 인증 없이 반환해야 한다. |
| 3 | 동의 상태 조회 | `GET /api/v1/user/consents`로 전체 항목의 최신 동의 상태를 반환해야 한다. |
| 4 | 선택 동의 변경 | `PUT /api/v1/user/consents/{type}`으로 선택 항목의 동의·철회를 append 기록해야 한다. 필수 항목은 가입 후 변경 불가. |

## 동의 항목·버전·저장 정책

### 설명

**동의 항목** — 아래 4종으로 정의한다.

| type | 이름 | 구분 | 대상 |
| --- | --- | --- | --- |
| `privacy` | 개인정보 수집·이용 동의 | 필수 | 계정 운영에 필요한 개인정보(카카오 회원번호·이메일·닉네임)의 수집·이용 |
| `audio_usage` | 음성 데이터 활용 동의 | 필수 | 면접 연습 음성 녹음의 수집과 **서비스 제공(면접 분석·피드백 리포트) 목적의 처리에 한정** — 모델 개선·연구 등 2차 활용 불포함 |
| `resume_usage` | 이력서 자료 활용 동의 | 필수 | 업로드한 이력서·자료의 수집과 **서비스 제공(면접 질문 생성) 목적의 처리에 한정** — 2차 활용 불포함 |
| `marketing` | 마케팅 정보 수신 동의 | 선택 | 이벤트·소식 등 마케팅 정보 수신 |

- **동의 시점 모델은 "가입 시 필수"를 채택한다**: 필수 3종에 전부 동의해야 가입·복구가 완료된다(검증은 HBB1-11의 `MISSING_REQUIRED_CONSENT` 계약). 채택 근거 — 음성·이력서 처리는 서비스의 본질 기능(이력서 → 질문 생성 → 음성 연습 → 분석)이라 이를 허용하지 않는 계정은 이용할 수 있는 기능이 없다는 기획 전제, 그리고 동의는 처리 허용의 선언일 뿐 실제 수집은 기능 사용 시점에 발생한다는 점. 기능 최초 사용 시점 동의 모델은 확장 검토로 두되, **음성·이력서 없이 쓰는 모드가 기획에 추가되면 이 모델은 재검토가 필수다**(본질 기능 논거가 무너져 해당 항목을 필수 동의로 유지할 수 없음).
- **필수 동의는 서비스 본질 기능 수행에 필요한 처리로 한정한다**: AI 학습·모델 개선·연구 등 2차 활용은 필수 동의에 포함하지 않으며(항목 표의 "불포함" 명시), 필요해지면 **별도 선택 항목**으로 추가한다. 음성에 화자 식별(생체인식) 용도가 생기는 경우도 같다 — 민감정보로서 별도 동의가 필요하다.
- 가입 후 필수 동의의 개별 철회는 지원하지 않으며, 철회 수단은 탈퇴다(탈퇴 시 일괄 `WITHDRAWN` — HBB1-10).
- 선택 항목은 가입·복구 시 미동의(`agreed: false`) 또는 미제출이 가능하고, 가입 후 변경 API(기능 4)로 동의·철회할 수 있다.
- 항목 집합은 MVP에서 4종으로 고정한다. 항목 추가(예: AI 학습·2차 활용의 선택 동의)는 확장 범위다 — 특히 신규 **필수** 항목 추가는 기존 유저의 재동의가 필요하므로 재동의 흐름(확장 범위)과 함께 설계해야 한다.

**동의서 버전** — `user_consent.version`은 "사용자가 어느 개정판 동의서에 동의했는가"를 남기는 audit 필드다.

- 항목별 현재 버전은 **설정**(`@ConfigurationProperties` record + compact constructor fail-fast — JwtProperties 패턴)으로 관리한다. 4항목 모두 기본값 없이 주입받으며, 미주입·1 미만 값은 기동 실패로 즉시 발견한다. 초기 버전은 전 항목 1이다.
- 현재 구현의 코드 상수(`AuthService.CONSENT_VERSION = 1`)는 이 설정 참조로 교체한다(가입·복구 경로 포함).
- **버전 확인 계약** — 기록되는 버전은 사용자가 **실제 확인한** 동의서의 버전이어야 한다. 요청 처리 시점의 서버 설정 버전을 그대로 기록하면, 프론트가 구버전 문서를 표시한 사이 서버가 새 버전으로 배포된 경우 사용자가 보지 않은 버전에 동의한 것으로 기록되어 audit 신뢰성이 깨진다. 이를 다음 계약으로 차단한다:
  1. 서버가 현재 동의 항목·버전을 제공한다(기능 2). 프론트는 동의 화면을 이 응답으로만 구성한다.
  2. 동의 제출(가입·복구의 `/auth/signup`, 선택 동의 변경)의 `agreed: true` 항목은 사용자가 확인한 `version`을 필수로 포함한다.
  3. 서버는 제출 버전을 현재 설정 버전과 대조해, 하나라도 다르면 `409 CONSENT_VERSION_MISMATCH`(U005)로 거부하고 아무 기록도 남기지 않는다. 프론트는 기능 2를 **캐시 우회로** 재호출해 최신 동의서를 다시 보여준 뒤 재제출한다(캐시 계약은 기능 2).
  4. 버전 검증은 필수 동의 검증(`MISSING_REQUIRED_CONSENT`)에 **선행**한다 — 사용자가 본 문서가 이미 낡았다면 그 화면에서 내린 다른 판정은 무의미하다. 요청 형태 검증(항목 중복·미지원 type 등 — oauth.md의 형태 규칙)은 그보다 앞선다(형태 400 → 버전 409 → 필수 동의 400).
  - 제출 버전은 클라이언트가 임의 값을 보낼 수 있으므로 신뢰 재료가 아니라 **대조 재료**다. 대조를 통과한 제출만 기록되므로 "기록 버전 = 서버 현재 버전 = 사용자가 확인한 버전"이 보장된다.
  - signup token에 발급 시점의 버전 세트를 담는 대안은 기각한다 — 토큰 발급(10분 유효) 후 문서가 개정되면 구버전 가입 허용 여부라는 별도 정책이 필요해진다. 제출 시점 대조는 이 엣지를 별도 정책 없이 흡수한다(개정되면 409 → 최신 문서 재확인 후 재제출).
- 기록 규칙:
  - `AGREED`는 **제출된 `version`**으로 기록한다(가입·복구·변경 공통 — 위 대조를 통과했으므로 현재 설정 버전과 같다. 복구 경로의 "최신 동의서 버전으로 기록" 요구 — HBB1-10 기능 4 — 는 이 계약으로 충족된다).
  - `WITHDRAWN`은 버전 확인 대상이 아니다 — 철회는 문서 확인을 전제하지 않으며, 철회 가능성이 문서 개정에 막혀서도 안 된다. 철회 대상인 **최신 `AGREED`와 동일한 버전**으로 기록한다("버전 N에 대한 동의를 철회했다"는 사실 기록 — 탈퇴 경로에서 확정된 규칙(HBB1-10 기능 3)을 변경 API도 공유한다).
  - 동의 이력이 없는 항목의 명시적 미동의(가입 시 `agreed: false` 제출)는 현재 설정 버전으로 `WITHDRAWN`을 기록한다(동의한 사실이 없으므로 버전 대조 불필요 — "버전 N이 시행 중일 때 미동의를 표시했다"는 기록).
- 버전 갱신 절차: 동의서 개정 시 설정의 해당 항목 버전을 올려 배포한다. 배포 후 구버전 화면에서의 제출은 409로 걸러지고, 이후의 `AGREED`는 새 버전으로 기록된다. 기존 유저의 구버전 동의는 유효한 것으로 유지한다(재동의 요구는 확장 범위).
- **버전 단조 증가(롤백 금지)**: 설정 버전은 인상만 허용하고 감소는 금지한다. 버전이 v2 → v1로 되돌아가면 v2 동의 이후에 v1 `AGREED`가 최신 행으로 기록되는 역행이 생길 수 있다. 잘못 인상한 경우에도 설정을 되돌리지 않고 **새 버전 발행으로 정정**한다(fix-forward — 문서 자산이 불변이므로 정정판도 새 버전이다). 선택 동의 변경 API는 기록 버전보다 낮은 버전의 `AGREED`를 append하지 않는 방어를 갖는다(기능 4).
- **배포 단위 제약(현재 버전의 단일 원천)**: 현재 버전의 원천이 인스턴스별 설정이므로, 버전을 변경하는 배포는 **구·신 버전 인스턴스가 동시에 트래픽을 받지 않도록**(전 인스턴스 동시 전환) 수행한다. 롤링 배포로 공존하면 — `GET /api/v1/consents`는 신버전, `/auth/signup`은 구버전 인스턴스에 도달하는 식으로 — 불필요한 409와 재조회·재제출 반복이 생길 수 있다. 이 창에서도 **정합성은 깨지지 않는다**(각 인스턴스는 자신의 현재 버전과 대조를 통과한 제출만 기록하므로 "기록 = 사용자 확인 버전" 불변식은 유지). 문제는 가용성이므로 운영 제약으로 관리하되, 수평 확장으로 동시 전환이 부담스러워지면 중앙 저장소(DB)를 현재 버전의 단일 원천으로 이관하는 것을 재검토한다(항목별 설정 채택은 MVP 규모 전제).
- **외부 계약 — 버전별 원문의 불변 보관·게시**: 버전 숫자는 당시 원문을 찾을 수 있을 때만 증거가 된다. 서버 범위 밖이지만 시스템 전체가 지켜야 하는 계약으로 명시한다:
  - 동의서 원문은 **버전마다 별도의 불변 자산**으로 게시·보관한다(프론트·운영 소유). 과거 버전의 삭제·덮어쓰기는 금지한다.
  - 보관 자산에는 원문과 함께 content hash를 남긴다(변조·유실 검증용 지문). 해시를 서버 설정에 두지는 않는다 — 서버가 생성하지도 검증하지도 않는 값이라 문서와 조용히 어긋나는(drift) 위험만 생기므로, 지문은 문서가 보관되는 곳에 함께 둔다.
  - **배포 정합성**: 버전 N의 문서 자산이 게시된 후에만 서버 설정을 N으로 인상한다. 프론트는 기능 2 응답의 버전 번호로 표시할 문서 자산을 선택하므로, 이 순서를 지키면 게시~인상 사이 창에서도 번호와 본문이 어긋나지 않는다(구버전 번호 → 구버전 자산 표시).

**저장 정책 (append-only)** — HBB1-11에서 구현된 방식을 본 문서가 계약으로 확정한다.

- 모든 동의·철회는 `user_consent`에 새 행으로 append하며, **서비스 경로에서** 기존 행의 UPDATE·DELETE는 금지한다. "언제, 어느 버전에, 동의·철회했는가"의 이력을 온전하게 유지하는 무결성 계약이다. 보존 기간 경과에 따른 파기·비식별화는 별개 축의 결정으로, 이 계약의 위반이 아니라 아래 보존 정책의 소관이다.
- 항목별 현재 상태는 해당 유형의 **최신 행**으로 판정하며, 최신 판정 기준은 `id`(대리키) 내림차순이다 — 한 트랜잭션이 남기는 행들은 동일 `created_at`을 갖도록 요구되므로(HBB1-10 공통: 시각 처리) 시각은 순서의 원천이 될 수 없다.
- 이력이 없는 항목(가입 시 미제출된 선택 항목)은 **미동의**로 판정한다. 미제출과 명시적 `agreed: false`는 의도된 구분이다 — 명시적 false는 "항목이 노출됐고 거부했다"는 증적(`WITHDRAWN` 기록)이고, 미제출은 "항목이 노출되지 않았다"(예: 항목 추가 이후의 구버전 클라이언트)로 이력을 남기지 않는다.
- append가 발생하는 경로는 가입·복구 제출(`/auth/signup` — HBB1-11·10), 탈퇴의 일괄 `WITHDRAWN`(HBB1-10), 선택 동의 변경(기능 4)이다.
- **보존 정책(미확정 — 영구 삭제 스토리에서 확정)**: 본 스토리는 동의 이력의 보존 기간을 확정하지 않으며, **확정 전까지 영구 보존을 전제하지 않는다**. 동의받았다는 사실의 증빙 필요(분쟁 대응)와 개인정보보호법 제21조의 파기 원칙(목적 달성·보유기간 경과 시 파기, 다른 법령에 따른 보존 시 분리 보관) 사이의 결정이 필요하므로, 아래 항목을 영구 삭제 스토리에서 **법무·개인정보 담당 확인을 거쳐** 확정한다:
  - 보존 기간·보존 근거·파기 시점
  - 탈퇴(파기) 시 `user_id`의 익명화 또는 별도 audit 식별자로의 치환 여부 — 이력 행에 직접 식별정보(이름·이메일 등)는 없지만, `user_id`는 `users`·`deletion_log`·백업·로그 등과 연결될 수 있는 안정적 식별자라 "직접 식별정보가 없다"는 것만으로 개인정보가 아니라고 단정할 수 없다
  - 보존 데이터의 분리 보관·접근 통제
  - 파기 배치의 `user_consent` 처리 방식(파기 대상 제외 여부 포함)

  본 스토리의 계약은 "서비스 경로가 이력을 변경·삭제하지 않는다"까지다. 탈퇴·파기 시점에 동의 이력이 일단 남는 것은 보존 결정이 아니라, 파기 정책이 확정될 때까지의 기본 상태다.

### 실행 조건

- `user_consent` 테이블이 존재해야 한다(HBB1-11에서 생성됨, 스키마 변경 없음).
- 항목별 동의서 버전 설정이 로드되어 있어야 한다.

### 검증 기준

- 버전 설정 미주입 또는 1 미만 값으로 기동 시 fail-fast로 기동이 실패하는지 확인
- 가입·복구·변경으로 append되는 `AGREED`가 제출·대조를 통과한 버전(=현재 설정 버전)으로 기록되는지 확인
- 현재 설정 버전과 다른 `version`을 포함한 제출(가입·복구·변경)이 `409 CONSENT_VERSION_MISMATCH`로 거부되고 계정·이력이 생성되지 않는지 확인
- 버전 불일치와 필수 동의 누락이 함께 있는 signup 제출이 400이 아닌 409로 거부되는지 확인 (버전 검증 선행)
- 설정 버전을 올린 뒤 새 버전으로 제출한 `AGREED`가 새 버전으로 기록되는지 확인 (설정 오버라이드 테스트)
- 변경 API의 `WITHDRAWN`이 철회 대상 `AGREED`와 동일한 버전으로 기록되는지 확인 (탈퇴 경로의 동일 규칙은 HBB1-10에서 검증됨)
- 어떤 서비스 경로도 기존 `user_consent` 행을 UPDATE·DELETE하지 않는지 확인 (변경 반복 후 기존 행 불변·행 수 증가만 발생)

### 성능 요구사항

- 없음 (정책 정의 — API 성능은 기능 2·3에서 규정)

### 인터페이스 요구사항

- 설정: 항목별 동의서 버전 4종 (기본값 없이 주입, 미주입 시 기동 실패)

### 제약사항

- 항목 집합은 4종으로 고정한다. 항목 추가·삭제는 확장 범위.
- 동의서 문서 본문의 작성·게시·버전별 보관은 서버 범위 외다. 서버는 버전 숫자만 기록한다.
- 동의서 버전은 단조 증가한다 — 설정 롤백 금지, 정정은 새 버전 발행(fix-forward)으로만 한다.
- 동의서 버전을 변경하는 배포는 롤링이 아닌 **전 인스턴스 동시 전환**으로 수행한다(운영 제약 — 수평 확장 시 DB 단일 원천 이관 재검토).
- 버전 갱신에 따른 기존 유저 재동의 요구 흐름(갱신 감지·재동의 화면·미동의 시 제한)은 확장 범위.

## 현재 동의 항목·버전 제공

### 설명

동의 화면이 검증 계약과 어긋나지 않기 위해 참조해야 하는 **검증 메타데이터의 원천**이다. `GET /api/v1/consents`는 전체 동의 항목의 `type`·`required`(필수 여부)·현재 `version`을 반환해야 한다.

- **소유 분담**: 서버는 검증 판정(400·409)의 재료인 항목 집합·필수 여부·현재 버전만 소유·제공한다. 표시 이름·동의서 본문(버전별 불변 자산 — 기능 1의 외부 계약)·표시 순서는 프론트가 소유한다 — 이 API만으로 동의 화면 전체를 구성하는 것은 아니다.
- **인증 불필요** — 가입 전(signup token 단계)의 동의 화면에서 호출되기 때문이다. 동의서 메타데이터는 특정 유저에 종속되지 않는 공개 정보라 노출 위험이 없다.
- 경로를 `/user/consents`(유저 종속 리소스 — 기능 3)와 달리 최상위에 두는 이유: 동의서 메타데이터는 유저 소유가 아니다(초안 ADR-009와 동일한 구분 기준).
- 프론트는 이 응답의 `version`으로 표시할 문서 자산을 선택하고, 제출 시 그 버전을 그대로 되돌려 보낸다(기능 1의 버전 확인 계약).
- **응답은 캐시되면 안 된다**(`Cache-Control: no-store`) — 버전 대조의 원천이라, 브라우저·CDN·프록시가 구버전 응답을 재사용하면 409를 받은 프론트가 재조회해도 같은 구버전을 받아 재시도 루프에 빠진다. 409 처리 시 프론트는 캐시를 우회해 재조회해야 한다.

### 실행 조건

- 항목별 동의서 버전 설정이 로드되어 있어야 한다.

### 검증 기준

- 4항목이 `type`·`required`·현재 설정 `version`과 함께 반환되는지 확인
- `required`가 필수 3종은 `true`, `marketing`은 `false`인지 확인
- 인증 없이 호출 가능한지 확인
- 설정 버전 변경이 응답에 반영되는지 확인 (설정 오버라이드 테스트)
- 응답에 `Cache-Control: no-store` 헤더가 설정되는지 확인

### 성능 요구사항

- 로컬 환경 기준 100ms 이내로 응답해야 한다.

### 인터페이스 요구사항

- 엔드포인트: `GET /api/v1/consents` (인증 불필요 — SecurityConfig 인증 예외 경로로 등록)
- 응답 헤더: `Cache-Control: no-store`

`GET /api/v1/consents` 응답 예시:

```json
{
  "success": true,
  "data": {
    "consents": [
      { "type": "privacy", "required": true, "version": 1 },
      { "type": "audio_usage", "required": true, "version": 1 },
      { "type": "resume_usage", "required": true, "version": 1 },
      { "type": "marketing", "required": false, "version": 1 }
    ]
  }

```

### 제약사항

- 동의서 문서 본문·URL은 응답에 포함하지 않는다(본문은 프론트·운영 소유 — 기능 1의 경계). 문서 URL 안내가 필요해지면 확장 범위로 검토한다.

## 동의 상태 조회

### 설명

인증된 사용자가 `GET /api/v1/user/consents`를 호출하면 서버는 AT의 userId로 본인의 동의 이력을 조회해, **전체 항목(4종)의 최신 상태**를 반환해야 한다.

- 항목별 최신 행(append-only, `id` 내림차순)을 기준으로 `type`·`agreed`·`version`·`updatedAt`을 구성한다. `agreed`는 최신 행의 action이 `AGREED`인지 여부, `updatedAt`은 최신 행의 기록 시각(마지막 상태 변경 시각)이다.
- 이력이 없는 항목도 응답에서 제외하지 않고 `agreed: false`, `version`·`updatedAt`은 `null`로 반환한다 — 이력 유무와 무관하게 전 항목의 현재 상태를 표현하기 위함이다. 본 API는 **상태 조회 전용**이며, 화면 구성에 필요한 메타데이터(필수 여부·현재 버전)는 기능 2와 조합해 사용한다(예: 설정 화면의 재동의 제출에 필요한 현재 버전).
- 읽기 전용 경로이므로 잠금은 불필요하다. 단 내 정보 조회(HBB1-10 기능 1)와 동일하게, 서비스 계층에서 방어적으로 `deleted_at IS NULL`을 확인해 어긋나면 401로 처리한다.

### 실행 조건

- 유효한 Access Token으로 인증된 상태여야 한다.

### 검증 기준

- 가입 직후 조회 시 제출한 동의 내역이 그대로 반영되는지 확인 (필수 3종 `agreed: true`, 제출한 선택 항목은 제출값대로)
- 가입 시 미제출한 선택 항목이 `agreed: false`·`version: null`·`updatedAt: null`로 반환되는지 확인
- 응답에 4항목이 모두 포함되는지 확인
- 동의→철회→재동의를 거친 항목이 최신 행 기준으로 반환되는지 확인
- `updatedAt`이 최신 행의 기록 시각과 일치하는지 확인
- 본인의 이력만 집계되는지 확인 (타 유저 이력 미포함)
- AT 없이 또는 무효한 AT로 호출 시 `401`이 반환되는지 확인

### 성능 요구사항

- 로컬 환경 기준 100ms 이내로 응답해야 한다.

### 인터페이스 요구사항

- 엔드포인트: `GET /api/v1/user/consents` (인증 필요, `Authorization: Bearer {accessToken}`)
- 모든 응답은 공통 envelope `ApiResponse<T>`로 감싼다(HTTP 상태코드는 바디에 넣지 않음).

`GET /api/v1/user/consents` 응답 예시:

```json
{
  "success": true,
  "data": {
    "consents": [
      { "type": "privacy", "agreed": true, "version": 1, "updatedAt": "2026-07-16T09:05:00Z" },
      { "type": "audio_usage", "agreed": true, "version": 1, "updatedAt": "2026-07-16T09:05:00Z" },
      { "type": "resume_usage", "agreed": true, "version": 1, "updatedAt": "2026-07-16T09:05:00Z" },
      { "type": "marketing", "agreed": false, "version": null, "updatedAt": null }
    ]
  }
}
```

### 제약사항

- 조회 대상은 본인의 **최신 상태**로 한정한다. 이력 전체(감사 로그) 조회 API는 범위 외.

## 선택 동의 변경

### 설명

인증된 사용자가 `PUT /api/v1/user/consents/{type}`에 `{ "agreed": true|false, "version": N }`을 전달하면, 서버는 **선택 항목에 한해** 동의·철회를 append 기록하고 전체 항목의 최신 상태(조회와 동일 형식)를 반환해야 한다. `version`은 사용자가 확인한 동의서 버전으로 `agreed: true`일 때 필수다(기능 1의 버전 확인 계약). 철회는 문서 확인을 전제하지 않으므로 `agreed: false`에서는 받지 않는다(전달돼도 검증·기록에 사용하지 않음).

아래를 **한 트랜잭션에서 이 순서대로** 수행한다.

1. 요청을 검증한다 — 알 수 없는 `{type}`이면 `400 INVALID_CONSENT_TYPE`, 필수 항목(`privacy`·`audio_usage`·`resume_usage`)이면 `400 CONSENT_NOT_CHANGEABLE`(도메인 에러 코드가 명시된 검증이므로 서비스 계층 검증 — HBB1-11에서 확립한 기준). `agreed: true`인데 `version` 누락이면 400(요청 형식 오류), 현재 설정 버전과 다르면 `409 CONSENT_VERSION_MISMATCH`로 거부한다(잠금이 필요 없는 검증을 잠금 앞에 배치)
2. **user 행을 잠그고 활성 여부를 재확인**한다(탈퇴됐으면 401). 유저 상태를 쓰는 다른 경로들과 직렬화 지점을 공유한다(HBB1-10 기능 2의 직렬화 계약, 잠금 순서 user → 후속 쓰기). 잠금 없이 append하면 탈퇴의 일괄 `WITHDRAWN`과 경합해 — 탈퇴가 최신 상태를 읽은 뒤 변경의 `AGREED`가 커밋되는 순서에서 — **탈퇴 완료 후 최신 상태가 `AGREED`로 남는** 정합 붕괴가 생긴다
3. Clock에서 트랜잭션 시각을 한 번 취득한다 — **잠금 획득 후에** 취득해야 한다. 잠금 전에 취득하면 잠금 대기 중에 다른 요청이 더 나중 시각으로 먼저 커밋해, 나중에 커밋된 최신 행이 더 오래된 기록 시각을 갖는 역행(`updatedAt` 후퇴)이 생긴다
4. 해당 항목의 최신 상태를 판정한다(이력 없음은 미동의로 간주). `agreed: false` 요청은 최신 상태가 미동의면, `agreed: true` 요청은 최신 행이 `AGREED`이고 그 기록 버전이 제출 버전 **이상**이면 **append 없이** 현재 상태를 반환한다(멱등 — 연속 중복 행 방지, 탈퇴의 중복 `WITHDRAWN` 방지와 동일 원칙. 기록 버전이 제출 버전을 **초과**하는 경우는 버전 단조 증가 위반의 신호이므로 WARN 로그를 남긴다 — 구버전 `AGREED`가 최신 행이 되는 역행을 쿼리 없이 흡수하는 방어). 최신 행이 `AGREED`이고 기록 버전이 제출 버전보다 낮으면 **새 버전에 대한 재동의**로 보고 append한다
5. append한다 — `AGREED`는 제출된 `version`, `WITHDRAWN`은 직전 `AGREED`와 동일 버전(기능 1의 기록 규칙)
6. 전체 항목의 최신 상태를 조회와 동일 형식으로 반환한다

- `agreed` 누락·null은 공통 bean validation(400)으로 거부한다(도메인 코드 불필요 — boolean 필수 필드).

### 실행 조건

- 유효한 Access Token으로 인증된 상태여야 한다.
- 항목별 동의서 버전 설정이 로드되어 있어야 한다.

### 검증 기준

- `marketing`에 `agreed: true`·현재 버전 요청 시 `AGREED`가 제출 버전으로 append되고 응답에 반영되는지 확인
- 현재 설정 버전과 다른 `version`의 `agreed: true` 요청이 `409 CONSENT_VERSION_MISMATCH`로 거부되고 이력이 생성되지 않는지 확인
- `agreed: true`인데 `version`이 누락된 요청이 `400`으로 거부되는지 확인
- 동의 상태에서 `agreed: false` 요청 시 `version` 없이 성공하고 `WITHDRAWN`이 직전 `AGREED`와 동일 버전으로 append되는지 확인
- 동일 상태·동일 버전 재요청(`AGREED` v1 상태에 `agreed: true`·v1)이 이력을 생성하지 않고 200과 현재 상태를 반환하는지 확인
- 설정 버전 인상 후 `AGREED` 상태 항목에 새 버전으로 `agreed: true` 요청 시 새 버전의 `AGREED`가 append되는지 확인 (새 버전 재동의)
- 기록 버전(v2)이 설정 버전(v1)보다 높은 상태(설정 롤백 위반 상황)에서 `agreed: true`·v1 요청이 append 없이 no-op 처리되고 WARN 로그가 남는지 확인 (역행 방어)
- 이력 없는 선택 항목에 `agreed: false` 요청 시 이력을 생성하지 않는지(미동의 = 동일 상태), `agreed: true` 요청 시 `AGREED`가 append되는지 확인
- 필수 항목(`privacy` 등) 변경 시도가 `400 CONSENT_NOT_CHANGEABLE`로 거부되고 이력이 생성되지 않는지 확인
- 알 수 없는 `{type}`이 `400 INVALID_CONSENT_TYPE`으로 거부되는지 확인
- `agreed` 누락·null 요청이 `400`으로 거부되는지 확인
- 변경 직후 조회 API 결과가 변경 결과와 일치하는지 확인
- 탈퇴된 유저의 변경 요청이 401로 거부되는지 확인
- 변경과 탈퇴가 동시에 실행돼도 탈퇴 완료 후 해당 항목의 최신 상태가 `AGREED`로 남지 않는지 확인 (동시성 통합 테스트)
- **동일 목표 상태**의 동시 변경 요청 두 건(예: 둘 다 `agreed: true`·같은 버전)은 이력이 1건만 생성되는지 확인 (동시성 통합 테스트)
- **반대 목표 상태**의 동시 변경 요청 두 건은 user 잠금 획득 순서대로 직렬 처리되어 — 순서에 따라 이력이 1건(선행 요청이 no-op인 경우) 또는 2건 — 최종 상태가 나중에 처리된 요청과 일치하고, 커밋된 상태 전환이 모두 이력에 남으며, 기록 시각이 `id` 순서에 대해 역행하지 않는지 확인 (동시성 통합 테스트)
- AT 없이 호출 시 `401`이 반환되는지 확인

### 성능 요구사항

- 로컬 환경 기준 100ms 이내로 응답해야 한다.

### 인터페이스 요구사항

- 엔드포인트: `PUT /api/v1/user/consents/{type}` (인증 필요)
- `{type}`: 동의 항목의 소문자 스네이크 표기(`marketing` 등 — 조회 응답의 `type`과 동일한 값)

`PUT /api/v1/user/consents/marketing` 요청:

```json
{ "agreed": true, "version": 1 }
```

`version`은 현재 동의 항목·버전 제공(기능 2) 응답에서 받아 화면에 표시한 동의서 버전이다. 철회(`agreed: false`)는 `version` 없이 보낸다. 응답 `data`는 동의 상태 조회와 동일 형식(전체 항목의 최신 상태).

### 제약사항

- 변경 가능한 항목은 선택 항목(`marketing`)으로 한정한다. 필수 동의의 철회는 탈퇴로만 가능하다.
- 항목 여러 개의 일괄 변경은 지원하지 않는다(항목당 요청 1회).

### 기타 요구사항

- 없음

## 공통: 시각 처리

- account.md의 공통 규칙(UTC `Instant` 통일, ISO-8601 `Z` 직렬화, 주입된 Clock 사용, 트랜잭션당 시각 1회 취득)을 그대로 따른다. 변경 API가 append하는 행의 기록 시각도 Clock에서 취득한 트랜잭션 시각이다.
- 시각 취득은 **user 행 잠금 획득 후**에 한다(기능 4 절차 참조) — 잠금 전에 취득하면 잠금 대기 순서와 시각 순서가 어긋나 최신 행의 기록 시각이 역행할 수 있다.

## 공통: 에러 코드

계정 도메인 에러 코드(접두사 `U`)에 아래를 추가한다. U001(INVALID_NAME)·U002(PURGE_IN_PROGRESS)는 account.md에서 정의됨.

| 코드 | 이름 | HTTP | 상황 |
| --- | --- | --- | --- |
| U003 | INVALID_CONSENT_TYPE | 400 | 알 수 없는 동의 항목으로 변경 요청 |
| U004 | CONSENT_NOT_CHANGEABLE | 400 | 필수 동의 항목의 변경 시도 (철회는 탈퇴로만 가능) |
| U005 | CONSENT_VERSION_MISMATCH | 409 | 제출한 동의서 버전이 서버 현재 버전과 불일치 — 최신 동의서 재확인 후 재제출 가능 |

- `CONSENT_VERSION_MISMATCH`는 `/auth/signup`(인증 도메인 엔드포인트)에서도 발생한다 — 에러 코드의 소속은 발생 엔드포인트가 아니라 에러의 도메인(동의)을 따른다.
- 가입·복구 제출의 필수 동의 누락(`MISSING_REQUIRED_CONSENT`)은 인증 도메인(`A`) 소속으로 oauth.md의 계약을 따른다.
- 인증 실패(AT 없음/무효/탈퇴 유저)는 기존 공통 401 처리를 따른다.
